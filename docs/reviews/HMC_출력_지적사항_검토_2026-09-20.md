# HMC 응답서 지적사항 검토

검토일: 2026-09-20. 대상: 현재 작업 트리(HEAD `fa81817`, 2026-09-14)와 저장된 `outputs/_supplychain/hmc/실사응답서_hmc_한울.xlsx`.

## 결론

저장본에서 제기된 출력 문제 대부분을 확인했다. 다만 9월 11일 이후 코드에 단위 환산·표시와 대표값 선택 변경이 들어 있어, 저장본의 문제와 현재 재현되는 결함을 구분해야 한다. D1의 방향성, 전력 비교쌍 누락, C-5의 질문 유형은 원래 지적의 설명을 수정해야 한다.

우선순위는 총량·부분값 및 기간/사업장 경계 보존, 재생에너지 비율의 검증 자격, 교차검증 결과의 응답 상태 전달이다. 정렬·요약·출처 표시는 별도 수정 대상이다.

## 검증 범위와 방법

- 저장된 한울/HMC Excel의 실제 셀 XML을 읽었다. 특히 응답서 A2, D25:F27, D54:F55와 정책 안내를 확인했다.
- 원본 시연용 가상 PDF 01 전기, 02 가스, 12 재생에너지의 전체 관련 페이지 텍스트를 확인하고 12번 문서는 이미지로도 확인했다.
- 12번 문서의 2026-08-05 저장 OCR 응답(`data/_cache/ocr/0ad49a4822ee713d7a36ba8cce53c0e31e9c47cf1eaf0f1cdb80cc137f318ce9.json`)을 현재 `_map_vlm_json → build_unified_graph → extract_with_ssot → build_data_points → build_response_sheet` 경로로 재생했다. 새로운 OCR/LLM API 호출은 하지 않았다.
- 전기·가스 결합 실험은 원본 수치를 `ExtractedMetric`에 넣은 재구성 입력이다. 과거 OCR 실행 전체를 그대로 복원한 결과로 해석하면 안 된다.
- 전체 비율이 추출되지 않은 경우는 저장 OCR 목록에서 10.6 항목을 제거하거나 태양광 비율 항목만 남긴 통제 실험이다.
- 기존 관련 테스트 73개 통과: `tests/audit_integrity/test_resolved_selection.py`, `tests/test_supplychain_responder.py`, `tests/test_kesg_evidence_requirements.py`, `tests/test_supplychain_drafter.py`.
- 이번 작업은 검토다. 제품 코드와 기존 응답서는 수정하지 않았다.

## 1. 에너지 단위와 산정 경계

**판정: 저장본 문제 확인. 현재 단위 환산·표시는 개선됐고 산정 경계는 미해결이다.**

저장본 D26은 `142560.0`, F26은 `142560.0kWh`, 기준 문항은 TJ다. 따라서 이 파일은 단위가 빠진 답변과 문항 메타데이터 사이의 제출 리스크가 있다. 내부 데이터가 실제로 142560 TJ로 저장됐다는 뜻은 아니다.

현재 정규 원장 경로는 `esgenie/ssot/ssot_pipeline.py:230`, `:288`에서 `normalize_to_item_unit`을 호출한다. 변환 구현은 `esgenie/ssot/node_select.py:655`에 있다. `Answer.display_value`는 단위와 연도를 붙이고 Excel/PDF가 이를 사용한다(`esgenie/supplychain/schema.py:120`, `exporters/excel.py:153`). 9월 11일 실제 실행 기록에도 142560 kWh → 0.513216 TJ가 확인된다(`docs/audit_integrity_20260911/result.md:86`).

원본 전기고지서는 **제1공장, 2026-04-25~05-24**이고 가스고지서는 **같은 기간, 제1공장 도장·건조라인**이다. 가스고지서에는 체적 8420 ㎥뿐 아니라 **사용열량 360772 MJ**가 명시돼 있다. 원문 표시 열량을 사용하면:

- 전기: 142560 kWh = **0.513216 TJ**.
- 가스: 360772 MJ = **100214.444… kWh = 0.360772 TJ**. 제기된 약 88800 kWh 대신 원문 열량을 사용해야 한다.
- 두 고지서의 에너지 합: **0.873988 TJ**. 이것도 해당 기간·해당 사업장의 두 에너지원 합이며 전사 연간 총량은 아니다.
- 코드의 예시 배출계수 적용: 전력 68.158 + 가스 20.239 = **88.397 tCO2eq**. Scope 1+2가 가스를 포함한다는 추정은 맞다(`esgenie/ssot/evidence_graph.py:267`, `:534`).

`select_fact_nodes`는 E-3-1 파생 배출량에만 합산 예외를 둔다(`esgenie/ssot/selection.py:46`). E-4-1은 하나의 대표 노드를 고르므로 전력·가스 총에너지의 완결성을 보장하지 않는다. 현재에는 `partial_value`·`derived` 등으로 자가신고에 낮추는 방어가 있지만, 답변에 정확한 월간 기간·사업장·에너지원 범위를 표시하거나 총량 미확정으로 보류하는 처리는 여전히 필요하다.

## 2. 재생에너지 5.6%와 검증 배지

**판정: 저장본의 잘못된 대표값과 검증 배지 확인. 현재는 항상 첫 행을 고르지 않지만 검증 자격 결함은 재현된다.**

저장본 D27/E27은 `5.6` / `✅ 증빙검증`이다. 원본 12번 문서는 5.6%, 3.8%, 1.2%뿐 아니라 §3에 **현재(2026 상반기) 재생에너지 비율 10.6%**를 직접 적었다.

현재 저장 OCR 재생 결과:

| 입력 | 현재 결과 | 상태 |
|---|---:|---|
| 저장 OCR 전체 | 10.6% | verified |
| 총비율 10.6 항목만 제거 | 1.2% | verified |
| 태양광 비율 항목만 유지 | 5.6% | verified |

`classify_common_value_role`은 비율/비중/률/율 표현을 총량으로 분류한다(`esgenie/ssot/node_select.py:289`). 따라서 태양광 비율과 기타 재생에너지 비율도 `total`로 분류된다. 현재 선택기는 순위·단위·연도·ID 등을 쓰므로 “무조건 첫 행”이 직접 원인은 아니다. 핵심은 부분 비율의 분모와 범위를 검증하지 못한다는 점이다.

또한 원본 자체에 **상반기 태양광 실적 45 MWh/월**과 **2026년 하반기 착공**이 함께 적혀 있다. 별도의 설비가 있는지는 문서만으로 확인되지 않는다. “그린 프리미엄” 행의 설명이 PPA 계약인 것도 조달수단 확인이 필요한 부분이다. 따라서 값을 10.6으로 바꾸는 것만으로 증빙검증이 정당화되지는 않는다.

“과소신고라 D1이 안 잡는다”는 설명은 현재 코드와 다르다. `mapping.py:210`은 절댓값 차이를 비교한다. 통제 실험에서 0% 대 10.6%도 불일치로 잡았다. 다만 5.6% 대 10.6% 차이는 5%p로 기존 10%p 임계값 아래라 **자가신고 일치**로 처리한다. 전체/부분의 의미 차이는 수치 허용오차로 해결할 수 없다.

## 3. 전기고지서와 720 MWh의 D1 비교

**판정: 범위 확인과 경고 전달의 결함은 있다. 실제 수치 불일치 또는 전력 계열 비교쌍 누락으로 단정할 수는 없다.**

- 전기고지서: 제1공장, 2026년 5월 청구분, 142.56 MWh.
- 12번 문서: 2026년 1~6월 월평균, 화석연료 기반 전력 720 MWh, 총 전력 805 MWh. 사업장 범위는 명시하지 않는다.

전사인지 단일 공장인지, 총 전력인지 구매 전력인지, 특정월인지 반기 평균인지가 다르거나 불명확하다. 현 상태에서 5배 차이를 곧바로 오류라고 판정하면 오탐이 된다. 범위 확인 필요로 보여줘야 한다.

폐기물 92% 대 29.3%는 `SupplierClaim`과 증빙의 비교이며 이 사례는 증빙끼리 비교라는 차이도 있다. SAQ 자동 주장 파서는 현재 재활용률만 추출한다(`esgenie/supplychain/claims.py:112`).

현재 그래프는 같은 지표/연도에서 출처 origin이 다르면 교차검증 엣지를 만들 수 있다. 따라서 구조화 전기고지서와 비정형 전력 현황의 비교가 원천적으로 제외된 것은 아니다(`esgenie/ssot/evidence_graph.py:515`). 결합 통제 실험에서도 엣지와 D1 0.4가 생성됐지만 답변은 자가신고이고 `flags=[]`였다. `build_data_points`는 0.4를 estimated로, 응답기는 estimated를 self_reported로 바꾼다(`esgenie/ssot/audit_trace.py:121`, `esgenie/supplychain/mapping.py:20`).

추가로 이 엣지의 차이는 단위 환산 없이 원시 숫자끼리 계산한다. kWh/MWh/MJ·에너지원·기간·사업장 경계를 먼저 맞춰야 하며, 엣지의 오차 자체를 정확한 불일치 근거로 사용할 수도 없다. 저장본 F26에도 D1 위험 0.4는 표시돼 있다. 이는 “아무 신호도 없음”보다 **신뢰도 하향만 있고 명시적 검토 사유가 없음**에 가깝다.

**판정: 현재도 확정 버그.** 저장본 A2의 68.1% + 0.0% + 21.3%는 89.4%다. 47문항 중 AI초안 5건인 10.6%가 빠져 있다.

현재 문항을 직접 조회한 결과:

| 문항 | qtype | 대표 K-ESG 코드 | 안내 |
|---|---|---|---|
| D-5 공정거래 | yes_no_evidence | G-6-1 | 해당 수치를 입증할 고지서·명세서·산정표 |

## 7. 답변 셀 단위와 숫자 형식

**판정: 저장본 확인, 현재 단위·연도 표시는 해결, 숫자 형식은 잔존.**

현재 Excel과 PDF는 `Answer.display_value`를 사용한다. 단위와 연도는 표시하지만 숫자 본체는 여전히 `str(value)`라 불필요한 `.0`이나 구분자 부재가 남는다(`schema.py:129`). 단순히 88.397처럼 소수 셋째 자리 값이 있다는 사실 자체가 오류는 아니며, 산정 정밀도에 맞는 표시 정책이 필요하다. 현재 period는 연도만 표현하므로 월간 범위는 별도 문제다.

## 8. AI초안의 내부 ID

**판정: 현재도 확인.** 생성 프롬프트가 `[chunk_id]` 인용을 요구하고, exporter가 본문을 그대로 싣는다. 출처 목록에도 node_id를 추가한다(`drafter.py:24`, `exporters/excel.py:143`, `exporters/pdf.py:274`). 검증용 내부 ID는 유지하되 제출 표시에서 출처 번호·문서명·페이지로 변환해야 한다.

## 9. E-7 초안의 문항 적합성

**판정: 저장본에서 확인, 현재 방어는 충분하지 않다.** D54는 노사 자료공개, 단결권, 선물·접대 모니터링, 신고 핫라인, 개인정보, ISMS 내용을 섞는다. 일부는 의사소통과 관련 있지만 공급사·고객 대상 방침/성과 전달 프로세스를 충분히 답하지 못한다. D55와 근로자 권리 내용도 겹친다. 참고로 현재 E-8의 정식 문항은 단결권만이 아니라 근로자·이해관계자 참여·구제접근이다.

현재 BM25 폴백에는 관련성 사전 게이트가 있으므로 “관련성 판단이 전혀 없다”는 설명은 아니다. 다만 전체 청크 묶음에 대한 YES/NO이고 개별 청크 정제가 아니다. 코드 일치 경로는 문항별 재순위 없이 해당 코드 노드들을 반환한다. 마지막 grounding 검사도 질문을 인자로 받지 않는다(`drafter.py:119`, `:193`, `:251`, `:336`). 근거에 있는 문장인지와 해당 문항을 충족하는 답인지의 검증을 분리해야 한다. 새 LLM 생성은 실행하지 않았으므로 개선된 검색에서 똑같은 문장이 다시 생성된다고 단정하지 않는다.

## 10. 현대차 라벨

**판정: 타당한 제품 표시 리스크.** `hmc.py:13`은 실제 현대차 질문지 문구·번호·하위 문항 확보를 TODO로 남겼다. 현재 구현은 RBA-42의 현대차 행동규범 영역 재배치이며 현재 제목은 `(RBA v8.0 기반)`이라고 표시한다. 실제 현대차 공식 실사 양식이라는 근거는 없다. “현대차 협력사 ESG 사전점검 — RBA v8.0 매핑 참고양식”처럼 용도와 비공식 매핑 성격을 명시하는 편이 정확하다.

## 11. 설계문서

**판정: 내부 불일치 확인.** `docs/공급망실사_출력_설계.md:26`은 KAP 88지표와 K-ESG 공급망 60항목을 구분한다. 같은 문서 `:47`~`:49`는 `hyundai.py`, `kap.py # K-Mobility(KAP) 60항목`이라고 적는다. 현재 실제 어댑터는 `hmc.py`이고 `kap.py`는 없다. 숫자·파일명을 바로잡고 계획과 구현 완료 범위를 나눠야 한다. 이 검토는 문서 내부의 모순을 확인한 것이며 KAP 최신 공식 지표 수를 외부 자료로 재검증한 것은 아니다.

## 수정 권고 순서

1. 에너지·비율에 기간, 사업장, 에너지원, 분모 및 실적/계획 구분을 보존하고 총량 검증 자격을 적용한다. 범위가 불명확하면 검토 사유를 출력한다.
2. D1 증빙 간 비교의 단위·범위 조건과 상태 전달을 수정한다. 부분 비율 의미 오류를 단순 숫자 오차 기준으로 통과시키지 않는다.
3. 헤더 승인 대기 표시, 자연 정렬, 문항별 증빙 안내, 내부 인용 ID의 제출 표시 변환을 수정한다.
4. E-7 문항 충족성 검사와 원본 시연 문서의 실적/계획 모순을 보완한다.
5. 양식 제목·설계문서를 정리하고 해당 수정 이후 저장 응답서를 재생성한다.
