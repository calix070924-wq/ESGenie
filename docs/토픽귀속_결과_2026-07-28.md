## 1. 원인 4가지

### (가) `_KEYWORD_MAP`이 13개 코드만 커버

옛 사전은 키워드 17개 / 코드 13개였다. E 영역 17항목 중 **E-2-1·E-2-2·E-3-2·E-7-1·
E-7-2·E-8-1·E-9-1·E-1-1·E-1-2·E-3-3·E-5-2가 아예 없다.** 없는 코드의 숫자는 근처
용어와 무관하게 있는 코드 중 아무 곳으로 흘러간다.

### (나) `"Scope"` → E-3-1 무조건

```python
"Scope": ["ghg", "E-3-1"],
```
Scope**3**를 Scope1+2로 보낸다. Δ=691.6% 발화의 직접 원인이다.

### (다) 최후 폴백이 문장 전체 스캔

```python
for kw, (topic, code) in _KEYWORD_MAP.items():
    if kw in sentence:          # 근처에 없어도 문장 어딘가 있으면 그 코드를 붙인다
        return topic, code
```
다지표 문장에서는 사실상 임의 배정이다. dict 삽입 순서대로 첫 히트를 돌리므로
"원부자재 102,462톤"에 `재생에너지`(E-4-2)가 붙는 식이다.

### (라) 숫자 정규식이 `Scope3 배출량`에서 `3`+`배`를 뽑는다

`배`가 단위 목록에 있고 `\s*`가 0칸을 허용해 `('3','배')`가 claim이 됐다.
trace의 `E-3-1: claim=3.0배 — 단위 불일치` 정체다.

## 2. 설계 — `search_terms` 단일 출처 + leftmost-longest

`kesg_items`에 이미 항목별 동의어가 큐레이션돼 있다(E-3-2 → `('Scope 3','기타 간접배출',
'가치사슬 배출','scope3')`). 사전을 새로 늘리지 않고 그걸 읽는다.

```
1) 정규화       공백 제거 + 소문자화 (텍스트·용어 양쪽)
2) 용어 필터    단위성 용어 제외(tco2eq·tj·kwh·ghg·re100·nox·bod·전력량 …) + 3자 미만 제외
3) 매치 수집    before-window(25자)에서 모든 용어의 (start,end,code) 스팬 수집
4) 겹침 해소    leftmost-longest — 시작이 앞선 것 우선, 같으면 긴 것
5) 선택         남은 스팬 중 끝이 가장 뒤(= 숫자에 가장 가까운) 것
6) before 없으면 after-window에서 같은 방식, 가장 앞선 것
7) 그래도 없으면 None  ← 문장 전체 폴백 제거
```

**4단계가 핵심이다.** `재생에너지 사용 비율`에서 `재생에너지`(E-4-2)와 `에너지사용`(E-4-1)이
**겹치되 포함관계가 아니다.** 포함관계만 걸러내면 더 길고 더 뒤인 `에너지사용`이 이겨
E-4-1로 간다. leftmost 우선이어야 E-4-2가 나온다(PR #44 G2의 최장 일치와 같은 계열).

인덱스는 **모듈 로드 시 1회** 구축한다(모호 처리 후 용어 262개, **61개 코드 전수 커버** —
옛 사전은 13개였다). 문장마다 재구축하면 D1이 문장 수 × 용어 수만큼 돈다. 실측 39 µs/문장.

### 모호 용어 처리

한 용어가 두 코드에 걸리는 경우가 2건이다.

| 용어 | 걸리는 코드 | 처리 |
|---|---|---|
| `이직률` | S-2-1(신규 채용 및 고용 유지) · S-2-3(자발적 이직률) | 항목명이 용어를 포함하는 S-2-3 채택 |
| `제3자 검증` | E-3-3(온실가스 배출량 검증) · P-3-1(ESG 정보공시 검증) | 갈리지 않음 → **용어 폐기** |

`kesg_items._ALIAS_UNIQUE`가 모호 별칭을 버리는 것과 같은 판단이다 — 임의 배정보다
비교를 건너뛰는 게 낫다.

### `topic` 문자열

`_match_topic_near`는 `(topic, code)`를 돌리고 `NumericClaim.topic`에 실린다.
저장소 전체에서 `topic`을 **읽는 곳이 없다**(필드에 담기기만 한다 — 확인함).
새 라벨 체계를 만들지 않고 `item.name`을 넣었다.

### 정규식

```python
_NUMBER_PATTERN = re.compile(
    r"(?<![0-9A-Za-z가-힣])"                       # 신설: 글자에 붙은 숫자 배제
    r"(?P<num>\d{1,3}(?:,\d{3})*(?:\.\d+)?)\s*"
    r"(?P<unit>%|억원|조원|tCO2eq|만\s*tCO2eq|톤|ton|TJ|%p|건|명|배(?!출))",
)
```
lookbehind가 `Scope3`·`RE100`·`IFRS S2` 류를 통째로 막고, `배(?!출)`이 `배출`의 `배`를
단위로 보지 않는다. 배수 단위 자체는 살아 있다(`전년 대비 3배 증가` → 여전히 추출).

**OCR 캐시(`feature/ocr-cache`)가 스택에 들어가 있으니 2회차부터 훨씬 빨라야 한다.**
1회차는 `OCR 캐시 : hit 0 / miss 87`, 2회차는 `hit 87 / miss 0`이 헤더에 찍힌다.
2회차가 1회차와 비슷한 시간이면 캐시가 안 먹은 것이므로 `docs/OCR캐시_결과_2026-07-27.md`

D1이 0.0으로 안 떨어지면 확인 순서:

1. detail에 어떤 코드가 남았는가 — 남은 코드가 §5의 사전 누락(S-3-1·G-2-1)인지
2. 원장값이 §3 표와 같은가 — 다르면 OCR 추출이 또 흔들린 것이다(캐시 mode 확인)
3. 같은 코드끼리 비교하는데 Δ가 크면 **이번 트랙 밖**이다(대표노드 선택 규칙 문제)
