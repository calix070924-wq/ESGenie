# 노드 정합성 실태 조사 (작업0) — L0/L1 매칭 정합성 개편 착수 전

조사일: 2026-07-23 · 브랜치: `feature/l0-matching-integrity`
목적: 설계안(`작업문서/L0매칭_정합성_개편안_2026-07-21.md`)이 8개 실측 사례 기반이라,
구현 전 실제 오염 분포를 측정해 설계를 보정한다.

## 0. 요약 — 설계와의 차이(구현 전 확인 필요)

| 항목 | 설계안 | 실태 조사 결과 |
|---|---|---|
| 단위 사전 미등록 | ML·㎥·m3 추가 | **실제 미등록은 TJ·kg·건·‰**. ML/㎥/m3는 kesg_items 어느 항목 단위에도 없음(용수는 `ton`으로 정의). **TJ가 핵심**(모비스 에너지 9,075 TJ 사례) |
| G2 최장 일치 효과 | 사례 8(자발적이직률) 차단 | `이직률`→S-2-3 이미 정상 매칭. 사례 8은 **코드 문제가 아니라 값 오류**(6.3 vs 12.7) — **어떤 L0 매칭 게이트로도 못 잡음** |
| 8사례 차단 규칙 | G1·G2·G3·G4·G6 분산 | **G1+G3만으로 7/8 차단**(시뮬). 사례 8만 미해결(범위 밖) |
| 전수 노드 덤프 | 5개사 그래프 로드 | **오프라인 불가** — 아래 §1 참조 |

**결론: 설계의 게이트 골격(G1 가드·G3 단위·G4 미래기간·G5 노드선택·G6 각주)은 유효**하나,
구현 세부에서 3가지 보정이 필요하다. 크게 뒤집히진 않으므로 **구현 진행 가능**하되,
아래 결정사항을 확정하고 시작한다.

## 1. 전수 노드 덤프 — 오프라인 재구성 불가 (작업0-1)

`scripts/audit_node_integrity.py`가 노드별 `value/unit/metric_hint`를 뽑으려면 evidence
graph가 필요한데:

- **그래프 덤프 파일 없음**: `outputs/`에 graph/node dump 0건.
- **audit_trace는 부족**: `evidence_node_ids`(303개)와 risk_vector는 있으나, node_id가
  `{corp}_{code}_{period}__{origin}__{hash}` 형태로 **metric_hint가 해시**돼 value·unit·원본
  라벨을 복원할 수 없다.
- **재구성 = 라이브 실행**: 실제 노드를 얻으려면 파이프라인(gpt-4.1-mini OCR 추출)을 다시
  돌려야 하고 이는 **과금 작업(금지)**.

→ **node_id로 복원 가능한 범위만** 집계했다(참여 노드 300개 기준, 전수 아님):

| 지표 | 값 |
|---|---|
| origin 분포 | `ocr_unstructured` 278 (93%) / `dart` 22 (7%) |
| future_period(>2025) | **0건** (참여 노드 전부 period=2025) |
| 상위 코드 | E-5-1(67) · E-4-1(45) · E-4-2(43) · E-6-1(32) · S-2-1(20) · S-4-2(19) |

- **오염이 ocr_unstructured에 집중**(93%)이라는 설계 전제는 재확인됨(DART 대조군은 clean).
- **future_period 0건**: D1에 *참여한* 노드엔 미래기간이 없다. 단, 이는 "D1 발화에 쓰인
  노드"만 본 것이라 G4(미래기간 분리)의 실효는 이 데이터로 판정 불가. 네이버 2040 사례
  (라벨링 §1)는 실재하므로 G4는 **예방적으로 유지**하되 효과 측정은 라이브 재실행 몫으로 남김.

**한계 명시**: 이 조사는 "D1이 실제로 비교에 쓴 노드"의 부분집합이다. 전체 노드(미공시로
남아 D1에 안 쓰인 것 포함) 분포는 라이브 재실행 없이는 못 구한다. 플래그별 전수 비율
(설계 §5의 "예상 효과"를 대체할 수치)은 **부분 관측**임을 전제로 읽어야 한다.

## 2. `_HINT_TO_KESG` 부분문자열 충돌 (작업0-2)

현재 사전 키 쌍 중 한쪽이 다른 쪽의 부분문자열인 경우 **4쌍**:

| 짧은 키 | 긴 키 | 판정 |
|---|---|---|
| 전력(E-4-1) | 사용전력량(E-4-1) | 동일코드 — 무해 |
| 정규직비율(S-2-2) | 비정규직비율(S-2-2) | 동일코드 — 무해 |
| 교육훈련비(S-2-4) | 1인당교육훈련비(S-2-4) | 동일코드 — 무해 |
| 복리후생비(S-2-5) | 1인당복리후생비(S-2-5) | 동일코드 — 무해 |

**판정이 뒤집히는 충돌 0건.** 즉 현재 사전 안에서는 최장 일치(G2)의 실익이 없다.

G2의 실제 가치는 **신규 키를 추가할 때** 생긴다:
- `용수 재이용률(%)` → 현재 `용수`(E-5-1, ton)에 걸림. G3 단위검증(% vs ton)으로도 차단되나,
  `용수재이용률→E-5-2` 키를 넣으면 **올바른 코드로 매칭**(차단이 아니라 정정)이 더 낫다.
- `재생에너지 사용·전환율` → `재생에너지`(E-4-2)에 정상 매칭. 신규 키 불필요.

→ **G2는 "신규 키 추가 + 최장 일치 순회"로 구현**하되, 목적은 과차단이 아니라 **정정**
(가능하면 올바른 하위 코드로). 신규 키 후보: `용수재이용률/용수재활용률→E-5-2`.

## 3. 단위 사전 커버리지 (작업0-3)

kesg_items 정량 항목에 등장하는 unit 전체와 등록 여부:

| unit | 등록 | 쓰이는 코드(예) |
|---|---|---|
| % | ✅ | E-4-2, E-5-2, S-3-1 … |
| ton | ✅ | E-5-1 |
| tCO2eq | ✅ | E-3-1 |
| 원 | ✅ | (비용 항목) |
| 명 | ✅ | (인원 항목) |
| 톤 | ❌→(별칭 필요) | E-6-1 (`톤`이 `ton`으로 정규화되는지 확인 필요) |
| **TJ** | ❌ | **E-4-1 (에너지 사용량)** — 모비스 9,075 TJ 사례 직결 |
| **kg** | ❌ | (일부 배출 항목) |
| **건** | ❌ | (건수 항목) |
| **‰** | ❌ | **S-4-2 (산업재해율)** — 삼성전기 재해율 사례 직결 |

**설계의 ML·㎥·m3는 실제 항목 단위에 없어 추가해도 실효 없음.** 대신 **TJ·kg·건·‰ 등록이
실제 사례를 좌우한다**. 특히:
- **TJ**: 에너지 그룹(TJ↔GJ↔MWh↔kWh) 환산 정의 필요. E-4-1이 TJ라 없으면 에너지 오매핑
  전부 판정 불가.
- **‰**: 등록해야 S-4-2(‰)에 % 값이 들어온 사례7을 G3로 차단. 단 ‰↔% 혼동은 실제 재해율
  표기 요동이 있어 **과차단 주의**(음성 테스트 필수).

## 4. 과차단 리스크 (구현 전 방어선 확인)

- **가드 어휘 vs 정상 항목명**: 정량 항목명에 가드어휘(목표·감축량·전환량·누적 등)가 포함된
  정상 K-ESG 항목 **0건** — 가드가 정상 항목을 막을 위험은 항목명 기준으로는 없음. 단 회사가
  '온실가스 감축량'을 별도 공시하는 경우는 여전히 막히므로, "감축량은 실적 총량 아님"이라는
  가드 의도는 정당(감축량≠배출량).
- **G3 ‰/% 환산**: 재해율의 ‰↔% 요동은 실존 → 음성 테스트로 정상 재해율이 안 막히는지 검증.

## 5. 8개 실측 사례 게이트 시뮬 (G1 가드 + G3 단위, TJ 등록 가정)

| # | 사례 | hint | 결과 | 차단 규칙 |
|---|---|---|---|---|
| 1 | 모비스 E-3-1 | 누적 온실가스 목표 감축량 | ✅차단 | G1 가드 |
| 2 | 모비스 E-4-1 | 재생에너지 전환량 | ✅차단 | G1 가드 |
| 3 | 모비스 E-5-1 | 용수←임직원수(명) | ✅차단 | G3 단위(ton≠명) |
| 4 | 네이버 E-3-1 | 온실가스 2040 전망 | ✅차단 | G1 가드('전망') |
| 5 | 네이버 E-5-1 | 용수←온실가스(tCO2eq) | ✅차단 | G3 단위(ton≠tCO2eq) |
| 6 | LG E-5-1 | 용수 재이용률(%) | ✅차단 | G3 단위(ton≠%) / G2로 E-5-2 정정 |
| 7 | 삼성전기 S-4-2 | 재해율 각주(4.0) | ✅차단 | G3 단위(‰≠ 무단위) / G6 각주 |
| 8 | 모비스 S-2-3 | 자발적 이직률 | ❌미해결 | **코드 정상, 값 오류 — L0 매칭 범위 밖** |

**7/8 차단**. 사례 8은 코드 해소가 아니라 값 자체가 틀린 것(6.3 vs 실제 12.7)이라 이번 개편의
어떤 게이트로도 잡히지 않는다 — 이는 표 추출/값 선택 문제(직전 PR #43 계열)이지 코드 매칭
문제가 아니다. 회귀 테스트에서 사례 8은 **"코드는 S-2-3로 정상 매칭됨"을 고정**하고, 값 오류는
범위 밖으로 명시한다.

## 6. 구현 결정 (이 조사로 확정)

1. **단위 확장**: TJ·kg·건·‰ 등록 + 에너지 환산 그룹(TJ↔GJ↔MWh↔kWh). ML/㎥/m3는 무해하나
   실효 없어 **생략**(또는 방어적 별칭만). `톤→ton` 별칭 존재 여부 확인 후 보강.
2. **G3 우선**: 최대 효과·최소 변경. `_unit_suspect` 재사용(중복 구현 금지).
3. **G1 가드**: 설계 목록 그대로. 정상 항목 충돌 0건 확인됨.
4. **G2**: 신규 키(E-5-2 재이용률) 추가 + 최장 일치. 과차단 아닌 **정정** 목적.
5. **G4/G5**: 예방적 유지. 효과는 라이브 재실행 몫(오프라인 측정 불가).
6. **G6 각주**: 정규식 1개 + 테스트로 한정(범위 축소 준수).
7. **사례 8**: 범위 밖 명시.
