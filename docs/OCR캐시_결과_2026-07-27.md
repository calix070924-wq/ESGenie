# 작업 1~5 결과 — OCR 결과 캐싱 (검증 재현성)

2026-07-27 · `feature/ocr-cache` (부모: `feature/l1-node-selection`, 미머지 스택)
조사: `docs/OCR_비결정성_조사_2026-07-27.md`

## 결론 먼저

**비정형 채널의 LLM 응답을 청크 단위로 캐싱한다. 키는 실제 LLM 입력의 sha256이다.**
같은 PDF를 두 번째로 돌리면 LLM을 한 번도 부르지 않고 지난 추출을 그대로 재현한다.

**이건 OCR을 결정적으로 만드는 게 아니다.** LLM 호출 자체는 여전히 비결정적이다
(캐시 미스일 때의 경로는 도입 이전과 100% 동일하다). 목표는 **검증 루프에서 OCR 변동을
상수로 고정**해, 규칙을 바꿨을 때 값이 달라진 원인이 규칙인지 추출 흔들림인지 갈리게 하는 것이다.
조사 문서 §1이 그 필요를 실측으로 남겼다 — 같은 PDF·`temperature=0.0`인데 hint 공통 비율 48.1%,
E-4-2가 규칙 변경 없이 12.9%(정답) → 10.0%(오답).

**캐시는 정확성을 대신하지 않는다. 틀린 추출을 고정할 뿐이다.** E-4-2가 10.0%로 굳으면
10.0%가 재현된다 — 재현은 되지만 여전히 오답이다. 정확도 교정(§7 범위 밖 항목)은 별도 과제고,
캐시는 그 과제를 **검증 가능하게** 만드는 전제 조건이다.

## 1. 캐시 키 설계 — 왜 코드 버전이 아니라 입력 해시인가

```python
cache_key = sha256(model_name + "\x00" + prompt + "\x00" + doc_type + "\x00" + llm_input_text)
```

`prompt`는 **전문**이다(`VLM_EXTRACT_SYSTEM` + `VLM_EXTRACT_PROMPT` 템플릿).
버전 문자열이 아니다. `llm_input_text`는 청크가 붙은 최종 `user` 메시지 전체다.

버전 문자열을 키로 쓰면 **찾기 매우 어려운 함정**이 생긴다. 전처리
(`_reconstruct_rows_from_dict`·`_inherit_label_rows`·`_attach_column_headers` — PR #43)를
고치면 LLM 입력이 달라지는데 키는 그대로다 → 낡은 응답이 돌아오고 → **전처리 개선이
"효과 없음"으로 보인다.** 입력 자체를 해싱하면 전처리를 한 글자 고치는 순간 키가 갈린다.

이 설계가 성립하는 근거는 **입력이 결정적이라는 측정**이다(조사 문서 §3):
`_extract_text_pymupdf`를 같은 PDF에 5회 → SHA256 5/5 동일(341,184자, 87청크).
입력이 흔들리면 키가 매번 달라져 캐시가 영구 미스가 되므로, 이걸 먼저 재고 설계를 확정했다.

키에 **넣지 않은 것**과 이유:

| 넣지 않음 | 이유 |
|---|---|
| 파일 경로 | 같은 내용의 파일은 같은 키여야 한다(복사·이동·재업로드 시 재과금 방지) |
| 타임스탬프 | 시각이 키에 들어가면 캐시가 영구 미스다 |
| 회사명·corp_code | 같은 문서를 다른 이름으로 넣어도 같은 추출이어야 한다 |
| 코드 버전 문자열 | 위 함정 |
| pymupdf 버전 | 버전이 바뀌면 추출 텍스트가 바뀌므로 **키가 이미 따라 바뀐다** — 중복이다 |

**청크 단위 키**다. 문서 하나에 87개 엔트리가 생긴다. 청킹 파라미터
(`_UNSTRUCTURED_CHUNK_CHARS=4000`)를 바꾸면 전 청크의 입력이 재분할돼 87개 키가 전부
새 키가 된다 — 자동 무효화.

### 1-1. 무효화 조건표

| 바뀐 것 | 캐시 | 왜 |
|---|---|---|
| PDF 내용 | **무효** | 추출 텍스트 → 입력 변경 |
| PDF 파일명·경로 | 유효(재사용) | 키에 없음 — 의도 |
| 전처리 코드(행 복원·헤더 상속·컬럼 매핑) | **무효** | 입력 텍스트 변경 |
| pymupdf 버전 | **무효** | 추출 텍스트 변경 |
| 청킹 파라미터 | **무효**(전 청크) | 청크 경계 변경 |
| 프롬프트 문구 | **무효** | 키에 프롬프트 전문 포함 |
| 모델(`OPENAI_MODEL`) | **무효** | 키에 모델명 포함 |
| `doc_type`(라우팅 판정) | **무효** | 키에 포함 |
| `_map_vlm_json` / G6 각주 배제 로직 | 유효 | **캐시 밖**이라 항상 재실행 → 즉시 반영 |
| `_augment_unstructured_clauses` | 유효 | 캐시 밖 |
| `_backfill_kesg_codes` / 동의어 사전 | 유효 | 캐시 밖 — 사전 갱신이 바로 반영된다 |
| 대표 노드 선택 규칙(`node_select`) | 유효 | L1이라 캐시와 무관 |

마지막 네 줄이 의도적 경계다. **캐시는 LLM 응답 직후(청크별 `metrics`/`clauses`)까지만
담는다.** 그 아래 결정적 후처리는 매번 다시 돈다 — 사전이나 게이트를 고쳤을 때 캐시를
지우지 않아도 반영되게.

## 2. 저장 위치와 파일 형식

`data/_cache/ocr/{sha256}.json` — `corp_codes.json`과 같은 부모(`data/_cache/`)다.

`.gitignore`에 `data/_cache/ocr/`를 추가했다. `data/_cache/corp_codes.json`은 이미 추적
중이므로 `data/_cache/` 전체를 무시하면 추적 파일과 충돌한다 — 하위 디렉터리만 무시한다.

엔트리 형식:

```json
{
  "schema": 1,
  "meta": {
    "key": "…64자…",
    "created_at": "2026-07-27T04:12:33+00:00",
    "model": "gpt-4.1-mini",
    "doc_type": "policy_manual",
    "source_file": "012330_mobis_2025.pdf",
    "prompt_sha256": "…",
    "input_chars": 3987
  },
  "extraction": { "…OcrExtraction.to_dict()…" }
}
```

`source_file`은 **키에 안 들어가고 meta에만 남는다** — 감사·정리용이다(어느 문서가 이 캐시를
만들었는지). `created_at`은 캐시를 지울 판단 근거다.

복원은 신규 `OcrExtraction.from_dict()`가 한다. `to_dict()`의 역변환으로 중첩 dataclass
(`ExtractedMetric`·`ExtractedClause`·`ExtractedTable`·`TableCell`)까지 복원하며,
**모르는 키는 무시**한다(스키마가 늘어난 캐시 파일도 예외 없이 읽힌다).

### 2-1. 환경변수

| 변수 | 기본 | 동작 |
|---|---|---|
| `ESGENIE_OCR_CACHE` | `1`(켜짐) | `0` → 읽기·쓰기 모두 안 함(완전 우회) |
| `ESGENIE_OCR_CACHE_REFRESH` | `0` | `1` → 읽기 건너뛰고 호출 후 **덮어쓰기** |
| `ESGENIE_OCR_CACHE_DIR` | `data/_cache/ocr` | 디렉터리 오버라이드(테스트 격리) |
| `ESGENIE_FORCE_MOCK` | `0` | `1` → **캐시를 읽지도 쓰지도 않는다** |

`ESGENIE_FORCE_MOCK=1`(테스트)에서 캐시를 끄는 이유: mock 응답이 이미 결정적이라 캐시가
필요 없고, 켜 두면 테스트가 실제 `data/_cache/ocr/`를 mock 산출물로 오염시킨다.
`tests/conftest.py`에서 `ESGENIE_OCR_CACHE_DIR`을 tmp로 격리하는 **이중 안전장치**도 걸었다
(캐시 경로를 직접 만지는 테스트가 생겨도 실 캐시에 닿지 않게).

### 2-2. 손상 캐시 처리

깨진 JSON·스키마 불일치·본문 없음·복원 실패는 **전부 조용히 미스로 떨어뜨리고 재호출**한다.
예외를 상위로 올리지 않는다 — 캐시는 보조 장치이므로 캐시 문제로 파이프라인이 죽으면 안 된다.
단 `logger.warning`으로 흔적을 남긴다:

```
OCR 캐시 파일 손상 — 무시하고 재호출 [ab12….json]: Expecting value: line 1 column 3
OCR 캐시 스키마 불일치 — 무시하고 재호출 [ab12….json]
```

쓰기 실패(`OSError`)도 무시한다(읽기 전용 마운트 등).

### 2-3. 캐시 디렉터리 관리 — 언제 지우나

한 문서당 청크 수만큼 파일이 생긴다(현대모비스 87개). `raw_text`는 청크 엔트리에 담지
않으므로(전체 텍스트가 청크마다 중복 저장되는 걸 피한다) 파일 하나는 보통 수 KB다.

| 상황 | 조치 |
|---|---|
| 전처리·프롬프트·모델을 바꿨다 | **지울 필요 없다** — 키가 달라져 새 엔트리가 생긴다. 옛 엔트리는 고아로 남을 뿐 |
| 고아 엔트리가 쌓여 용량이 거슬린다 | `rm -rf data/_cache/ocr/` — 다음 실행이 라이브 1회로 재생성한다(과금 발생) |
| 추출이 이상해 라이브를 다시 보고 싶다 | 지우지 말고 `ESGENIE_OCR_CACHE_REFRESH=1`로 돌려라(덮어쓰기) |
| 캐시 없이 현행 동작을 확인하고 싶다 | `ESGENIE_OCR_CACHE=0` — 파일을 건드리지 않는다 |
| 디스크 정리 | `created_at`이 오래된 것부터. 재생성 비용은 문서당 라이브 1회 |

## 3. 캐시 히트 노출 — 세 곳

캐시 히트를 감추면 "왜 값이 안 바뀌나"를 디버깅할 수 없다. 세 지점에서 보인다.

**(1) `router_meta`**

```python
ext.router_meta["ocr_cache"]         # "hit" | "miss" | "refresh" | "disabled"
ext.router_meta["ocr_cache_hits"]    # 청크 히트 수
ext.router_meta["ocr_cache_misses"]  # 청크 미스 수
```

부분 히트(87청크 중 80히트/7미스)는 `"miss"`로 라벨한다 — 한 청크라도 라이브 호출이
있었다는 뜻이고, 그러면 그 청크의 추출은 지난 실행과 다를 수 있다.

**(2) `pipeline.run` 로그**

```
[OCR] 캐시 hit 87 / miss 0 (mode=on)
```

`_collect_ocr_extractions` 직후, 문서 전량 합계다(`ocr_cache.summarize`).
추출기 내부에서도 문서별 `logger.info("[OCR] 캐시 %s — hit %d / miss %d [파일]")`를 남긴다.

**(3) `inspect_ledger_provenance.py` 헤더**

```
==============================================================================
L1 원장 출처 점검 — 현대모비스 (00164788) · report_year=2025
영역 E · 항목 12개 · 그래프 노드 171개
OCR 캐시 : hit 87 / miss 0  (mode=on)   ← 전량 캐시 리플레이 (추출 고정)
==============================================================================
```

`--json` 출력에도 `"ocr_cache": {"mode":…, "hits":…, "misses":…}`를 넣었다.
`ocr_diff.py`로 두 스냅샷을 비교할 때 "왜 달라졌는가"의 1차 판정 근거가 된다 —
한쪽이 miss였다면 규칙이 아니라 추출이 달라진 것이다.

라벨 3종: `← 라이브 추출 포함 (다음 실행부터 재현)` / `← 전량 캐시 리플레이 (추출 고정)` /
`← 캐시 경로 미사용 (mock/구조화 채널)`.

## 4. 비교 도구 — `scripts/ocr_diff.py`

두 `ledger_provenance_*.json`을 대조해 추출 변동의 폭을 잰다(조사 문서 §4에 v2 vs v3
기준선 출력을 남겼다 — hint 공통 비율 **48.1%**).

```bash
python3 scripts/ocr_diff.py outputs/lp_pass1.json outputs/lp_pass2.json
python3 scripts/ocr_diff.py a.json b.json --codes E-4-1 E-6-1 --show 8
```

캐시가 작동하면 두 스냅샷의 판정이 `완전 동일 — 재현됨`, `hint 공통 비율 100.0%`,
`전체 노드 Δ0`이어야 한다. **48.1% → 100%가 이 트랙의 성공 조건이다.**

## 6. 사용자 검증 절차 (라이브 1회 + 리플레이 1회)

캐시가 실제로 일하는지는 **2패스**로만 확인된다.

**1패스 — 캐시 채우기(라이브, 과금 1회):**

```bash
time python3 scripts/inspect_ledger_provenance.py --ticker 012330 --areas E \
     --json outputs/ledger_provenance_012330_pass1.json
```

기대: 헤더 `OCR 캐시 : hit 0 / miss 87  (mode=on)   ← 라이브 추출 포함`.
`data/_cache/ocr/`에 87개 파일 생성(`ls data/_cache/ocr | wc -l`).
L0+L1만 도니 L2~L5 LLM은 타지 않는다 — 비용은 OCR 1회.

**2패스 — 리플레이(무과금):**

```bash
time python3 scripts/inspect_ledger_provenance.py --ticker 012330 --areas E \
     --json outputs/ledger_provenance_012330_pass2.json
```

기대: 헤더 `OCR 캐시 : hit 87 / miss 0  (mode=on)   ← 전량 캐시 리플레이 (추출 고정)`.

**3. 차이 0 확인:**

```bash
python3 scripts/ocr_diff.py outputs/ledger_provenance_012330_pass1.json \
                            outputs/ledger_provenance_012330_pass2.json
```

기대:

```
  전체 노드      : L N → R N  (Δ+0)
  hint 공통 비율 : M/M = 100.0%
  hint 집합이 바뀐 코드 : 0개 / 12개
  같은 hint 값 변화     : 0건
  판정 : 완전 동일 — 재현됨
```

**보고할 것 — 경과 시간.** `time`의 실측치를 두 패스 모두 적어라.
캐시가 실제로 먹었다면 2패스가 1패스보다 **극적으로 짧다**(LLM 87회 호출이 사라진다.
1패스가 30~50분이면 2패스는 pymupdf 추출+L1 시간만 남는다). 시간이 비슷하면
`ocr_cache` 라벨이 `hit`이라도 뭔가 잘못된 것이므로 로그를 봐야 한다.

**진단 순서**(2패스가 `miss`로 나오면):

1. `ls data/_cache/ocr | wc -l` — 0이면 1패스가 저장을 못 했다(권한·경로 로그 확인)
2. `env | grep ESGENIE_OCR` — `ESGENIE_OCR_CACHE=0`이나 `_REFRESH=1`이 남아 있는지
3. `env | grep ESGENIE_FORCE_MOCK` — `1`이면 캐시가 통째로 꺼진다
4. 위가 다 정상인데 miss면 **입력이 실행 간에 달라진 것**이다 — 조사 문서 §3의
   pymupdf 결정성 확인 스니펫을 돌려 SHA256을 비교해라

**주의**: 1패스의 추출이 틀렸으면 그 오답이 고정된다. 캐시는 재현성만 준다.
1패스 값이 §1 기대값과 다르면(v3의 E-4-2 10.0% 같은 경우) `ESGENIE_OCR_CACHE_REFRESH=1`로
다시 뽑는 게 아니라, **추출 정확도 과제로 넘겨야 한다** — 재추출은 또 다른 난수일 뿐이다.
