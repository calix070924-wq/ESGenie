> 기준 커밋: `c2ad53e` (main, PR #53 머지 상태). 브랜치 `feature/d2-precision`.
> 실측 도구: `scripts/measure_d2_impact.py` (신설, LLM 호출 0회)

## 결론 (3줄)

1. **(가) 분모=1은 건드리지 않는다.** git 이력상 명시적 캘리브레이션 기록은 없으나,
   **실측 결과 분모를 4로 바꾸면 held-out test 룰 단독 F1이 0.532 → 0.255로 반토막**
   난다(recall 0.494 → 0.157). 주석("4개 = 만점")이 코드보다 틀렸을 가능성이 크다.
2. **(나)(다) 문맥 면제는 벤치에 영향이 없다.** 벤치 320문장(dev 50 + test 270)에
   해당 유형이 **0건**이다 — 안전하게 고칠 수 있다.
3. 분모 재설계는 **held-out 실키 재측정을 포함한 별도 과제**로 남긴다(§5).

## 1. 분모의 의도 — git 이력

```python
density = len(hits) / max(D2_THRESHOLD * 4, 1)   # 4개 = 만점 기준
```

| 항목 | 확인 결과 |
|---|---|
| 도입 커밋 | `39c60ac feat(L3): 5축 리스크 벡터 분해 (D1~D5)` (2026-04-27) |
| 수정 이력 | **없음.** `git log -L 559,559:esgenie/layer3_detect.py` → 커밋 1건 |
| `D2_THRESHOLD` 도입 | `b78525a feat(v10): v10 공유 스키마 + 임계값 상수 추가` (2026-04-27, 같은 날) |
| `D2_THRESHOLD` 값 변경 | **없음.** 도입 시부터 `0.25` |
| `calibrate.py` 그리드 | `trigger` · `rule_weight` · `threshold` · `axis_flag` **4개만**. `D2_THRESHOLD`는 그리드에 **없다** |

### 판단: "직접 튜닝된 값"은 아니지만 "그 위에서 캘리브레이션된 값"이다

`D2_THRESHOLD`는 그리드서치 대상이 **아니었다.** 즉 "분모=1이 최적이라 골랐다"는 기록은
없다. 다만 `calibrate.py`의 4개 손잡이(`BASELINE = trig 0.25 / w 0.4 / thr 0.25 / axf 0.80`)는
**분모=1인 D2 분포 위에서** 튜닝됐다. 특히 `axis_flag=0.80`은 "D2 단일 축 강신호" 게이트인데,
분모=1일 때만 히트 1개가 이 게이트를 넘는다. 분모를 4로 올리면 히트 1~3개가 전부 게이트
아래로 떨어져 **axis_flag 경로가 사실상 죽는다** — 아래 실측이 그 결과다.

`D1_THRESHOLD`(0.15)는 `score = worst_delta / D1_THRESHOLD` 형태로 **의미가 있는** 정규화
분모지만, D2의 `max(D2_THRESHOLD * 4, 1)`는 `D2_THRESHOLD=0.25` 하에서 항상 상수 1.0으로
접힌다. `D2_THRESHOLD`를 0.25 **아래로** 내리면 `max(..., 1)` 바닥에 갇혀 값이 아예 무의미해지고,
**위로** 올릴 때만(>0.25) 분모가 움직인다 — 환경변수 오버라이드가 반쪽만 작동하는 상태다.

## 3. (가) 분모 — 실측 결과: **바꾸면 안 된다**

D2 정의만 갈아끼우고 나머지는 전부 고정한 스윕:

### 룰 단독 (결정적, 전건)

| D2 정의 | dev F1 | dev P/R | **test F1** | test P/R |
|---|---|---|---|---|
| **현행 (분모 1.0)** | 0.808 | 0.677 / 1.000 | **0.532** | 0.577 / 0.494 |
| 분모 2 (2개 만점) | 0.808 | 0.677 / 1.000 | **0.532** | 0.577 / 0.494 |
| 분모 4 (주석 의도) | **0.933** ↑ | 0.875 / 1.000 | **0.255** ↓↓ | 0.684 / 0.157 |

**dev는 올라가고 test는 반토막 난다.** 이게 정확히 held-out 분리가 잡아내려는 패턴이다 —
dev(합성 튜닝셋 n=50)는 양성 문장에 모호어를 3~5개씩 몰아넣은 케이스가 많아 분모를 올려도
recall 1.0이 유지되지만, test 양성 83건의 히트 분포는 다르다:

| 히트 수 | test 양성 | test 음성 |
|---|---|---|
| 0개 | 42 | 159 |
| **1개** | **28** | 24 |
| 2개 | 11 | 4 |
| 3개 | 2 | 0 |

**실제 그린워싱 문장의 절반 이상(41/83)이 모호어 1~2개다.** 분모 4에서는 히트 1개 → 0.25,
2개 → 0.5로 `axis_flag=0.80`을 못 넘고, D2 가중치 0.25만으로는 `threshold=0.25`도 못 넘어
28+11건이 통째로 미탐이 된다(TP 41 → 13).

임계값을 D2 정의별로 **재튜닝해도** 하이브리드 test F1은 0.533 → 0.588로 소폭 오를 뿐이고
(`axf=0.90 thr=0.35`), 그건 held-out에서 임계값을 사후 조정하는 것이라
`docs/held_out_eval_methodology.md` §5가 금지한 행위다.

### 그래도 분모=1은 이상하다 — 다만 방향이 반대다

분모 1은 **"모호어 1개 = D2 만점"**이라 정보량이 없는 이진 검출기다
(히트 1개와 5개가 같은 점수). 개선 여지는 있지만, 실측이 말하는 개선 방향은
**분모를 올리는 것이 아니다** — 히트 1개도 실제 양성에서 흔하기 때문이다.
설계를 바꿔야 할 축은 분모가 아니라 **어휘 카테고리별 가중**(`match_categories`가 이미
absolute/condition/abstract/vague를 나누는데 점수는 쓰지 않는다)이다. §5로 이월.

**→ 결론: 이번 작업에서 (가)는 수정하지 않는다.** 주석만 현재 동작과 어긋난 채로 두면
다음 사람이 또 같은 오판을 하므로, **주석을 실제 동작과 실측 근거로 교체**한다(코드 변경 없음).

## 4. (나)(다) 유형 — 벤치 영향 0건

### (나) K-ESG 항목명 × 모호어 사전 겹침

`kesg_items` 전 항목의 `name` + `search_terms`를 `ALL_VAGUE`와 대조:

| 코드 | 표현 | 겹친 모호어 | 출처 |
|---|---|---|---|
| E-9-1 | `친환경 인증 제품/서비스` | 친환경 | **name** |
| E-9-1 | `친환경 인증` | 친환경 | search_terms |
| E-9-1 | `친환경 제품` | 친환경 | search_terms |
| E-9-1 | `녹색인증` | 녹색 | search_terms |
| E-1-1 | `탄소중립 목표` | 탄소중립 | **name** |

`name` 기준으로는 **2건**(E-9-1, E-1-1). 지시서는 E-9-1 1건으로 봤는데 E-1-1
`탄소중립 목표`도 같은 자책골 경로다 — L2가 "탄소중립 목표 항목의 공개가 필요하다"를
쓰면 똑같이 D2가 발화한다.

### 벤치 케이스 내 등장 건수

| 유형 | dev (n=50) | test (n=270) |
|---|---|---|
| (나) 겹치는 항목명(E-9-1·E-1-1)이 문장에 등장 | **0** | **0** |
| (다) 모호어 직후 조직 접미(팀·부·실·본부·위원회·센터·추진단) | **0** | **0** |

참고: 항목명이 등장하는 케이스 자체는 dev 21건 / test 2건 있으나(`재생에너지 사용 비율`,
`폐기물 재활용 비율` 등) **모호어와 겹치지 않는 항목명**이라 면제 대상이 아니다.

**→ (나)(다) 문맥 면제는 벤치 F1을 바꿀 수 없다.** 라이브 오탐만 제거된다.

## 5. 이월 — 분모 재설계 (별도 과제)

이번 범위 밖. 착수 조건과 설계 방향:

- **착수 조건**: held-out test 실키 재측정(`ESGENIE_STRICT=1 python scripts/held_out_eval.py`,
  n=270 전건 capture) — 판정 캐시가 test 56건만 덮는 현 상태로는 하이브리드 영향을 못 본다.
- **설계 방향**: 분모 상향이 아니라 **카테고리 가중**. `match_categories`가 이미
  absolute(절대형·검증불가) / condition(전제조건 누락) / abstract / vague로 나누는데
  점수 계산은 개수만 센다. `탄소중립`(absolute) 1개와 `적극적`(vague) 1개가 같은 1.0인 게
  실제 문제다.
- **부수 정리**: `D2_THRESHOLD` 환경변수가 0.25 이하에서 `max(..., 1)` 바닥에 갇혀
  무의미하다. 카테고리 가중으로 갈 때 이 상수의 역할을 다시 정의할 것.
