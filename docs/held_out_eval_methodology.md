# Held-out 평가 방법론 & 결과 (2026-06-14, 2026-07-12 데이터 확대분 갱신)

> **2026-07-12 갱신 고지**: test셋이 트랙 A/B/C 배치로 n=153→**n=270**(esg_report clean
> +101, regulatory_ad greenwash +16)까지 확대되었다. §2·§3의 수치는 이 확대 후 실키
> (`ESGENIE_STRICT=1 python scripts/held_out_eval.py`, gpt-4.1-mini, 2026-07-12 실행)
> 기준으로 갱신했다. §4의 서술(도메인별 텍스트분류 한계 논지)은 그대로 유효하나 안에 박힌
> 예시 수치(46건/10건)는 2026-06-14 시점 n=56 데이터 기준이라 낡았다 — 최신 도메인 분포는
> §2·§3을 참고할 것.

## 1. 설계 — 왜 dev/test를 분리했나

기존 50케이스 벤치마크는 **임계값 튜닝과 성능 평가를 같은 데이터로** 했다(과적합).
검수 데이터를 단순히 합쳐 신뢰구간을 다시 돌리면 낙관 편향이 그대로 남는다. 그래서:

- **dev (50케이스)** — 임계값 튜닝에 쓴 셋. 성능 상한(낙관 편향 가능).
- **test (56케이스, held-out)** — 검수 확정 라벨로만 구성. 임계값을 **고정**(재튜닝 금지)하고
  일반화 성능만 측정.

임계값은 dev에서 고정: `trigger=0.25, rule_weight=0.4, threshold=0.25, axis_flag=0.80`.

## 2. 결과 (실키 gpt-4.1-mini, 부트스트랩 95% CI)

**최신(2026-07-12, n=270) — 트랙 A/B 확대 후:**

| | dev (튜닝셋, n=50) | test (held-out, n=270) |
|---|---|---|
| F1 | 1.000 (CI 1.000–1.000) | 0.522 (CI 0.404–0.629) |
| Precision | 1.000 (CI 1.000–1.000) | 0.938 (CI 0.833–1.000) |
| Recall | 1.000 (CI 1.000–1.000) | 0.361 (CI 0.259–0.468) |

**확대 전(2026-07-11 이전, n=153) — 참고용:**

| | dev (튜닝셋, n=50) | test (held-out, n=153) |
|---|---|---|
| F1 | 0.977 (CI 0.914–1.000) | 0.568 (CI 0.442–0.683) |
| Precision | 0.955 (CI 0.842–1.000) | 0.964 (CI 0.882–1.000) |
| Recall | 1.000 (CI 1.000–1.000) | 0.403 (CI 0.289–0.524) |

**dev → test F1 격차는 확대 후에도 여전히 크다(1.000 vs 0.522).** held-out 분리가 없었다면
dev 1.0을 성능으로 오인했을 것이라는 §1의 결론은 변함없다. 확대 후 test F1(0.522)이 확대 전
(0.568)보다 오히려 낮아진 이유는 recall 하락(0.403→0.361) 때문이며, 이는 **트랙 B에서 추가한
16건(ASA 출처, 영어 기업 마케팅 문구)이 모두 탐지기에 미탐(FN)됐기 때문**이다(§3 참고).
Precision은 0.964→0.938로 소폭 하락했으나 CI가 겹쳐 유의미한 변화로 보기 어렵다.

**가장 오래된 기준선(2026-06-14, n=56)도 참고로 남겨둔다** — 지금은 완전히 대체된 값이지만
문서 이력 추적용으로 보존: F1 0.842(CI 0.600–1.000) / Precision 0.889(CI 0.615–1.000) /
Recall 0.800(CI 0.500–1.000).

## 3. 헤드라인 지표 — 동일도메인 특이도

test의 구성은 비대칭이다(2026-07-12, n=270 기준):
- **음성 187건 = 전부 실제 ESG 보고서 clean 문장**(동일도메인, 12개사 실보고서에서 수집).
- **양성 83건** = 기존 esg_report/greenwash 27건(문서 내부 비교용 별건, §4 참고) +
  **regulatory_ad(교차도메인) 56건**(기존 40건 한국어 위주 + 신규 16건 ASA(영국) 출처 영어
  기업 마케팅 문구).

따라서 지표를 도메인별로 정직하게 분리한다:

- **동일도메인 특이도 = 0.989**(187건 중 185건 정확 통과, CI 0.973–1.000) — 확대 전(n=153
  시점 부분집합 기준 재계산 0.988, CI 0.965–1.000)과 사실상 동일 수준을 유지하면서 **표본이
  2배 이상 늘어 CI 폭이 0.035 → 0.027로 좁아졌다.** "진짜 보고서 언어를 그린워싱으로
  과검출하지 않는다"는 핵심 강점이 더 넓은 기업·업종 표본(제조 5개사·금융 2개사·유통 2개사·
  IT 3개사)에서도 재확인됨.
- **교차도메인(regulatory_ad) recall = 0.393**(56건 중 22건 적중, CI 0.268–0.518) —
  확대 전(n=153 시점 부분집합 기준 재계산 0.550, CI 0.400–0.700)보다 **점추정치가 뚜렷이
  하락**했다. CI 폭 자체는 0.300 → 0.250으로 좁아졌지만(표본 40→56), 방향은 하락이다.
  원인은 아래 참조.

**원인 분석 — 신규 16건(TRKB-001~016, ASA 출처) 전건 미탐(FN), risk_score=0.125로 균일:**
기존 40건(한국어, "100% 생분해"·"무공해" 등 직접적 절대 표현 위주)과 달리, 신규 16건은
영어 기업 마케팅 문구("PROTECTING ITS FUTURE", "Sustainable Materials", "Eco-Friendly LNG
Technology" 등)로 서구 광고 표준(ASA)이 실제로 위반 판정한 사례들이다. 16건 전부가 동일한
낮은 risk_score(0.125)를 받아 **규칙 기반 1차 신호(lexicon)가 영어·완곡화된 절대 주장에는
거의 반응하지 않는 것으로 보인다.** 이는 데이터 확대 이전에는 드러나지 않았던 실제 일반화
격차이며, 즉시 임계값을 조정해 "고치지" 않고 캘리브레이션 신호로 그대로 남긴다(§5).

기존 esg_report/greenwash 27건(§4, 문서 내부 판정 불가 원칙과 별개로 참고 측정)도 19건
미탐 — 대부분 "앞장서겠습니다/최선을 다하고 있습니다"류 정량 근거 없는 리더십 수사 표현과,
기존에 알려진 생분해/분해 주장 패턴(KORP 5건)이었다.

남은 esg_report 오탐 2건: EXT-PDF-02(risk 0.525, 화학물질 재활용 정량 문장), **TRKA-015**
(risk 0.501, 이번 트랙 A에서 추가한 현대모비스 플라스틱 재활용 문장 — 2인 라벨링에서는
clean으로 합의됐으나 검출기는 강한 정량 표현("1만 9,320톤", "56.9%") 때문에 오탐. 라벨
오류라기보다 검출기가 수치가 강조된 정상 실적 문장에 과민 반응하는 패턴으로 해석).

## 4. 보고서 도메인 recall을 텍스트 분류로 재지 않는 이유

held-out test에는 동일도메인(ESG 보고서) **양성이 사실상 없다**. 후보 풀(8개사 보고서)을
전수 검토한 결과:

- 가장 그린워싱처럼 보이던 환경 수치도 검증하면 **사실 주장**이었다.
  예) 아시아나 "탄소 25% 적다 / 연료 15% 향상" → A350 vs B777, A321neo vs 구형의
  **제조사 스펙(정확)** → clean.
- 나머지(친환경 매출 22%, 전기차 100%, 자체 배출기준 50% 등)는 **수치가 증빙과
  일치하는지**에 따라 양성/음성이 갈리며, 문장만으로는 판정 불가.

즉 **보고서 그린워싱은 텍스트 분류 문제가 아니라 증빙 그라운딩 문제다:**
- 수치 주장 ↔ 실측값 불일치 → **D1 (numeric mismatch)**
- 유리한 항목만 공시·불리한 항목 누락 → **D6 (selective disclosure)**

이 두 축은 **증빙 기반 트랙**(증빙 그래프와 대조)에서 평가하며, 본 텍스트 분류 CI의
대상이 아니다. 본 CI는 **"정상 보고서 언어를 과검출하지 않는가(특이도)"** 와
**"노골적 텍스트 그린워싱(광고형)을 잡는가(교차도메인 recall)"** 를 측정한다.

## 5. 한계 & 다음 단계

- test 양성 표본이 작아(2026-07-12 기준 regulatory_ad n=56) recall CI가 여전히 넓다

  원본 보고서 PDF + 증빙(DART/본문) 대조가 필요하다 — 별도 트랙으로 분리.

## 6. 증빙-그라운딩 트랙 (evidence-grounding recall) — §4·§5의 후속

§4에서 미뤄둔 "증빙 기반 트랙"을 별도 측정 스크립트로 정식 편입했다
(`scripts/evidence_recall_eval.py`, 골드 `data/benchmark_v2/evidence_recall_gold.json`).
본 텍스트분류 CI 가 측정하지 못하는 축 — **K-ESG 코드 → 올바른 증빙 노드/조항 검색 재현율** — 을 잰다.

- **데이터**: 한울정밀공업 시연 증빙 PDF(전기·가스·폐기물·사내규정). 실 양식·가상 수치.
- **실측 경로**: `ocr_router`(정형→Azure Document Intelligence / 비정형→gpt-4.1-mini)
  → SSOT `EvidenceGraph` / `TextNode` → `layer1._match_evidence_nodes` 와 **동일한 키워드·검색 호출**.
- **before/after**: before = 코드만(`[code]`), after = 코드 + `KESGItem.search_terms`
  (ESGReveal `<SearchTerm>`). 코드단위 recall 을 부트스트랩 95% CI 로 산출.
- **추출 vs 검색 분리**: OCR 가 증빙을 정량 노드/정성 조항으로 뽑았는지(추출)와
  그 정답 ID를 코드로 검색해냈는지(검색)를 분리 집계 → SearchTerm 의 순수 검색 기여만 격리.

**왜 '실측'인가**: Azure 키가 연결된 환경에서만 OCR 이 실엔진으로 돌고, 키가 없으면
mock 으로 떨어져 리포트에 "실측 아님" 경고가 박힌다(held_out_eval 과 동일 규약).
즉 프록시·합성이 아니라 실제 OCR 출력 위에서 잰 수치라, 심사·데모 근거로 바로 쓸 수 있다.
SearchTerm 기여가 0 으로 나와도(= LLM/화이트리스트가 코드를 모두 해소) 그 자체가 정직한 결과다.

결과 리포트: `outputs/benchmark/evidence_recall.md`.
