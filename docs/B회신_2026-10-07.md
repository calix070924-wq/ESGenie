## 3. 버전·호환성 — A의 구체적 제안

| 제안 | 내용 |
|---|---|
| 버전 | **`1.1-draft` → 회신 후 `1.1`** |
| 왜 2.0이 아닌가 | 규칙상 `decision` 값 집합 변경은 주 버전 올림 사유다. 다만 1.0은 외부에 확정 배포된 적 없는 **`-draft`**였고, 바꾼 것은 "합의된 1.0"이 아니라 초안이다 |
| 오독 위험 | 읽는 쪽은 **주 버전만** 본다(`SUPPORTED_MAJOR = "1"`). 1.0-draft 문서를 읽으면 `decision`에 6값이 들어 있어 `bad_value`로 **걸린다** — 조용히 잘못 읽히지 않는다 |
| 호환 방침 | 1.0-draft 문서를 자동 변환해 주지 않는다. 변환기는 상세 상태만 정하면 되므로 양쪽 모두 재작성 범위가 작다 |
| 다른 판단이면 | **B가 2.0으로 올려야 한다고 보면 그 판단을 따른다.** A가 혼자 정하지 않는다 |

**회신을 받은 뒤** `docs/공통답안형식_v1.1초안_2026-10-07.md` §9에 확정 버전·B 확인
일자·C-1~C-6 회신·**기준 커밋 SHA**를 적어 고정한다. 그 전에는 비워 둔다.

| 함께 줄 것 | ① 열람한 파일 목록과 해시 ② 열람 일시 ③ 작성자 ④ A의 초안·메모를 보지 않았다는 확인 ⑤ **어느 입력 세트를 본 것인지**(세트 이름·ZIP 해시) |

### 5.1 입력 세트가 바뀌었다 — 기준을 명시해 달라

2026-10-07에 증빙 5건(14~18)이 추가됐다. **문항은 그대로 48문항 × 2단계 = 96행**이고
표본 목록도 바뀌지 않는다. 바뀐 것은 **보고 판단하는 입력**뿐이다.

- 기존 01~13과 자료요청안내는 A가 sha256으로 대조해 **14/14 바이트 동일**을 확인했다.
  따라서 이전 판단의 근거가 무효가 되지는 않는다. 다만 추가 5건이 **일부 문항의 요건을
  새로 덮으므로** 두 세트의 라벨 결과를 **한 표에 섞지 않는다.**
- A도 기존 세트 라벨(v1)을 보존한 채 새 세트 라벨을 **별도 버전**으로 만든다.
- **확인 필요(A → B):** 전달받은 ZIP 이름 `한울정밀_정상5건보강_라벨링용_20261007.zip`과
  해시 `d8bcc23e…0025d09`에 해당하는 파일이 A 쪽에 **도착하지 않았다.** A가 가진 것은
  `한울정밀_촬영세트_정상5건보강_20261007.zip`(sha256 `81853707…03e900b3`)이다.
  **라벨링용 ZIP 본체와 해시를 다시 확인해 주기 바란다.** 그때까지 추가 5건이 B 전달본과
  동일하다고 A가 확정하지 않는다.

- **제출 전까지 A의 초안 CSV·판단 메모·확인요청 문서를 공유하지 않는다.** 패키지
  빌더(`scripts/build_b_package.py`)의 금지 경로에 `data/eval/labels_draft/`를 넣어
  두었다.
- 제출 후 **협의 전 양측 값을 각각 보존**하고, 불일치 행 목록과 **기존 독립성 제외
  기준을 적용한** 일치율을 A가 계산해 공유한다. 협의 결과로 제출 전 값을 덮어쓰지
  않는다.

## 6. 회신 일정 — 알려 주면 A가 맞춘다

## 7. B 범위로 남기는 것
