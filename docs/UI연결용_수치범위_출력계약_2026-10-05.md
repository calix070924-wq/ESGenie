### 보고서 본문(LLM) — 0b770df

**바꾼 문구.** 생성 문장·제목·표 행·요약·확인 목록의 작성 문장을 원장·원문 확인 수치·생성 문맥 청크와 값·단위·참여 역할(대상·참석·미참석)·고용형태·날짜·사업장으로 대조한다(0d6a130). 인용 표기가 없으면 생성 문맥 전체가 근거 범위다. 확인된 오류는 그 자리에서 아래 문구로 바뀐다.

- `[확인 보류] 생성 문장의 수치(…)는 … 이 문장을 본문에 싣지 않았습니다.` 뒤에 `같은 문장에서 확인된 값: …`과 `원문 확인 값: 라벨 N명(날짜) — 출처; …`이 이어진다. 사유 부분은 `인용 근거·원문 확인 수치에서 찾지 못해`(orphan_number) 또는 `원문에서 다른 날짜·고용형태(집단)…의 값으로만 확인돼`(relation_mismatch, `problems`에 따라).
- 표에서는 틀린 칸만 `[확인 보류]`로 바뀌고 머리글·빈 칸·옆 값·비고는 그대로다.
- `[범위 미확정] {지표} {값}는 원문 범위(…)로만 확인된 참고값이며, 요청 기간·사업장의 확정 실적인지 확인하지 못했습니다(사유).`
  - 표에서는 칸에 `[범위 미확정: 원문 범위로만 확인된 참고값]`이 붙고, 머리글 `확정 실적`은 `실적`으로 바뀐다.
  - 제목에서는 `(범위 미확정 참고값 — 요청 범위의 확정 실적 아님)`이 붙는다.
- `[범위 주의] {지표} {값}의 원장 범위는 …이며 전체·연간·합산 값이 아닙니다.`

**`[검토: …]` 표시.** 판단이 갈리는 경우에만 붙는다: 목표 문장, 값 없이 범위 낱말만, 단위 없는 숫자, 지표를 특정하지 못한 값.

**결정적 표.** `### 원문 확인 수치(K-ESG 코드 없음)`(항목·값·기간·출처)는 LLM을 거치지 않는다. 교육 날짜별 인원·공정 스크랩 합계 등이 여기 실린다.

**감사 기록.** `report_body_review.json`과 `ReportDoc.meta.body_reviews`에 들어 있다. 행마다:

- `block`·`area`·`reason`(orphan_number / relation_mismatch / source_only_stated / scope_widened)·`action`(replaced / marked)
- `model_text`(모델 원문)·`output`(바꾼 문구)·`numbers`·`quantities`·`related`·`problems`·`cited`·`missing_citations`·`conflicts[{evidence, problems}]`·`code`
- `block="source_review"` 행은 확인 목록 작성 문장의 처리 기록이다(`finding_id`).
- `action="evidence_selected"` 행(본문 불변): 위 §0 참조. 감사 보기에서 "채택 근거 / 기각 후보"로 보인다.

**UI 표시 원칙.** 바꾼 문구와 표시를 지우거나 숨기지 않는다. 모델 원문은 감사 보기에서만 보인다.

## 3-1. 실행 출처(`run_info`) — 2026-10-06 추가(B-2)

이 출력물을 **어느 코드로** 만들었고 **신규 AI 처리인지 캐시 재생인지**를 출력물 자체에서 알 수 있게 한다. `esgenie/run_info.py`의 `build_run_info(...)`가 만들고, `result.json`의 최상위 `run_info` 키에 들어간다(`sheet`와 나란히). 화면 표시는 PR #65에서 붙인다.

```json
"run_info": {
  "commit_sha": "d8a0de8a434e…",        // 알 수 없으면 "unknown"
  "dirty": false,                        // 미커밋 변경 여부. 알 수 없으면 null
  "generated_at": "2026-10-06T20:48:13+09:00",   // KST
  "models": {"llm": "gpt-4.1-mini", "llm_provider": "openai|azure_openai",
             "ocr": "document-parse", "ocr_provider": "upstage_document_parse",
             "ocr_vlm": "gpt-4.1-mini"},
  "keys": {"openai": "설정됨", "anthropic": "없음", "upstage": "설정됨"},
  "processing": {
    "label": "신규 처리",                // 신규 처리 | 캐시 재생 | 혼합
    "llm": {"hits": 0, "misses": 17, "live_calls": 17, "successes": 17,
            "failures": 0, "mode": "on", "from_snapshot": true},
    "ocr": {"hits": 0, "misses": 10, "mode": "miss"},
    "upstage": {"live_requests": 4, "replay": false, "counted": true},
    "upstage_replay": false                // 이전 판 호환 자리(= upstage.replay)
  }
}
```

| 필드 | 뜻 |
|---|---|
| `commit_sha` / `dirty` | 출력물을 만든 코드. `dirty`가 참이면 커밋되지 않은 변경이 섞였다는 뜻이므로 화면에서 함께 보여야 한다. git을 쓸 수 없으면 `"unknown"` / `null` |
| `models.ocr` | **Upstage Document Parse 모델**이다. `models.ocr_vlm`(OCR 결과 보정에 쓰는 LLM)과 섞지 않는다 |
| `keys` | **값이 아니라 설정 여부만** 담는다(`설정됨`/`없음`). 비밀키는 어디에도 싣지 않는다 |
| `processing.label` | 판정 순서: ① LLM `live_calls == 0` ∧ OCR `misses == 0` ∧ **Upstage 실요청 == 0** → `캐시 재생` ② LLM `hits == 0` ∧ OCR `hits == 0` ∧ **Upstage 재생 아님** → `신규 처리` ③ 그 밖 → `혼합`. 아무것도 부르지 않은 실행은 ①에 먼저 걸려 `캐시 재생`이 된다 |
| `processing.llm.from_snapshot` | `llm_cache.stats()`는 프로세스 누적값이다. 실행 시작 스냅샷과의 차이로 센 경우 `true`, 누적값을 그대로 쓴 경우 `false` — **`false`면 숫자가 그 실행만의 값이 아니다.** 화면에서 수치를 보일 때 이 값을 함께 봐야 한다 |
| `processing.upstage.live_requests` | Upstage에 실제로 보낸 요청 수. **모르면 `null`** |
| `processing.upstage.replay` | Upstage 원시 응답을 기록에서 재생했는가(새 OCR 호출 없음) |
| `processing.upstage.counted` | 요청 수를 셀 수 있었는가. `false`면 `캐시 재생` 판정을 쓸 수 없다 — 화면에서도 "Upstage 실요청 확인 못 함"으로 보여야 한다 |

### 판정식이 작업지시서 §3과 다른 점 — Upstage 항을 더했다

작업지시서 §3의 판정식은 LLM·OCR 두 캐시만 본다. 그런데 **`ocr_cache`는 Upstage 응답 캐시가 아니라 Upstage 결과를 입력으로 받는 VLM 보정 LLM 응답 캐시**다. 코드 순서가 그것을 강제한다:

| 위치 | 하는 일 |
|---|---|
| `esgenie/ssot/ocr_router.py:1917` `extract_unstructured` | PDF 텍스트를 뽑고, 텍스트 레이어가 없으면 |
| `:1941` | **Upstage Document Parse를 호출**한다 |
| `:1977` `_extract_unstructured_text` | 그 텍스트를 받아 |
| `:2034` | 그것을 `llm_input`에 넣어 **OCR 캐시 키를 만들고** |
| `:2042` | 캐시를 조회한다 |

Upstage 결과가 캐시 키의 입력이므로 **순서가 바뀔 수 없다.** 그래서 OCR 캐시가 전부 적중해도 Upstage는 매번 실제로 불린다 — P1-0 followup 실측에서 **OCR 적중 10 · 미스 1인데 Upstage 요청 4건이 성공**했다. 두 항만 보면 **Upstage를 실제로 부른 실행이 `캐시 재생`으로, Upstage 기록을 재생한 실행이 `신규 처리`로** 찍힌다. Upstage 자체의 재생은 `ocr_cache`가 아니라 `live_numeric_rehearsal.py`의 `UpstageTape`(record/replay)가 맡는다.

`upstage.counted`가 `false`(요청 수를 모름)일 때는 **`캐시 재생`으로 판정하지 않는다**. 모르는 것을 재생이라고 말하지 않기 위해서다. 나머지 두 조건으로 `신규 처리` 판정은 허용한다.
| `timings` | `PipelineOutput.timings`가 있을 때만 들어간다(없어도 동작한다) |
