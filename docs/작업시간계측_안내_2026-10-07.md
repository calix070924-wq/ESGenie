# 작업시간 계측 안내 — 기계 시간과 사람 시간 (2026-10-07)

작업지시서 A §3.1~§3.3 구현에 대한 안내다. **UI 타이머는 만들지 않았다**(§3.2). 사람
기록은 CSV로 받는다.

## 0. 세 가지 시간을 섞지 않는다

| 양 | 어디서 나오는가 | 누가 적는가 |
|---|---|---|
| **기계 시간** (파이프라인 단계별 초) | `esgenie/run_timing.py` → `PipelineOutput.timings`, 실행 폴더의 `timings.json` | 코드가 `perf_counter`로 잰다 |
| **사람 작업시간** | worklog CSV의 `처리대기`가 아닌 단계 | **사람이 적는다** |
| **대기시간** | worklog CSV의 `처리대기` 단계 | **사람이 적는다** |

관계는 하나뿐이다:

```
실제 경과시간(elapsed) = 사람 작업시간(human) + 대기시간(wait) + 빈 시간(idle)
```

**기계 시간은 이 식에 더하지 않는다.** 기계가 도는 동안 사람은 `처리대기`를 적고 있다.
둘을 더하면 같은 시간을 두 번 센다. 집계 결과에서 기계 시간은 `machine_total_seconds`로
**따로** 적히고, 사람이 적은 대기보다 길면 `pipeline_exceeds_wait` 경고가 붙는다 — 그때
합산으로 메우지 않고 **기록 누락을 확인한다.**

겹친 구간도 두 번 세지 않는다. 사람 작업시간은 구간의 **합집합** 길이이고, 겹쳐서
덜어낸 양은 `overlap_removed_seconds`로 함께 적힌다. 기다리는 동안 다른 문항을 입력했다면
그 시간은 **사람 작업시간으로만** 센다(대기에서 뺀다).

## 1. 기계 시간 — 무엇이 기록되는가

`timings` 한 행의 모양:

```json
{"stage": "L2_rag_index", "seconds": 1.546, "backend": "sbert", "items": 56,
 "llm_cache_delta": {"failures": 0, "hits": 0, "live_calls": 0, "misses": 0, "successes": 0}}
```

- `_`로 시작하는 행(`_pipeline_total`, `_run_total`, `_probe_total`)은 **합계 행**이고
  `staged_sum`에 들어가지 않는다. 포함하면 합계가 합계를 다시 더해 두 배가 된다.
- `L0_ocr_extract` 행에는 `ocr_cache: {hits, misses, mode}`가 들어간다.
- 실행 폴더의 `timings.json`에는 `cache_profile`이 함께 적힌다 — **실행 모드는 실제
  플래그에서 적는다**(`upstage_replay` / `upstage_replay_live_llm` / `direct_live`).
  추정해서 쓰지 않는다. 이것으로 **캐시 재생 실행과 신규 처리 실행이 갈린다.**

파이프라인 단계(현재 16개): `L0_dart_load`, `L0_ocr_extract`, `L0_graph_build`,
`L1_extract`, `D6_ISSB`, `L2_embedding_backend`, `L2_rag_index`, `L3-L4_verify`(영역별),
`L5_trace_build`(영역별), `v15_artifacts`, `source_review`, `L6_report_export`,
`L5_trace_save`, `_pipeline_total`.
호출 스크립트(`scripts/live_numeric_rehearsal.py core`)가 덧붙이는 단계:
`saq_claims_parse`, `respond_sheet`, `result_json_write`, `evidence_pack_copy`,
`export_xlsx`, `export_pdf`, `_run_total`.

## 2. 사람 기록 양식

양식: `data/eval/worklog_template.csv` (헤더만 들어 있다 — **예시 시간을 넣어 두지
않았다.** 합성 시간이 실제 기록으로 오인되면 안 된다.)

| 열 | 값 |
|---|---|
| `session_id` | 리허설 세션 식별자 |
| `participant` | 참가자 식별자 |
| `method` | `manual` / `esgenie` |
| `request_round` | `1` / `2` |
| `qid` | 문항 ID |
| `step` | `원문확인` / `값입력` / `수정` / `보완자료정리` / `출력` / `처리대기` |
| `start`, `end` | **ISO 8601 날짜+시각** (`2026-10-20T09:00:00`) |
| `reused_from` | 앞 세션 결과를 재사용했으면 그 `session_id` |
| `run_dir` | `esgenie` 방식일 때 대응되는 실행 폴더 |
| `note` | 자유 기술 |

**시각에 날짜를 반드시 넣는다.** 시각만 적으면 자정을 넘긴 구간이 음수가 되고, "다음
날이겠지" 하는 임의 보정이 필요해진다. 그 보정은 하지 않는다 — `23:40`처럼 적으면
`bad_start`로 걸린다.

빈 `end`는 **추정하지 않는다.** `missing_end`로 적고 합산에서 뺀다. 합산 가능한 행이
없는 세션은 `0초`가 아니라 **`산출 불가`(`null`)** 로 적힌다.

## 3. 집계

```bash
python scripts/aggregate_worktime.py data/eval/worklog/*.csv \
  --read-run-dirs --out /tmp/worktime.json
```

`--read-run-dirs`는 `run_dir`의 `timings.json`에서 기계 시간을 읽어 **비교용으로만** 적는다.

절감률·단일 점수는 계산하지 않는다. `manual`/`esgenie`는 나란히 적는다
(§3.2: 1명 리허설 결과로 절감률을 주장하지 않는다). 출력 JSON에 비율 필드 자체가 없다.

| ② 단계 합 ≤ 전체 경과 + 캐시 재생/신규 예시 | **통과 — 합성 입력 + 실제 호출 1건** | `scripts/verify_timing_cache_modes.py`(공개 DART 샘플 + 합성 프로브) **그리고** `scripts/verify_timing_ocr_live.py`(실제 OpenAI 호출 1건 → 캐시 재생 1건). 기록: `docs/validation/eval-timing-20261006/ocr_live/`. 모든 기록이 `staged_sum ≤ seconds` |
| ③ 집계 스크립트 테스트 | **통과** | `tests/test_eval_worktime.py` 15건 — 겹치는 구간, 빈 `end`, 날짜 넘는 구간, 중복 합산 금지 포함 |
| ④ 리허설 1회 기록 | **미실시** | 사람 참가자가 필요하다. **AI가 시간을 만들어 적지 않는다**(§5) |

**② 실제 호출로 확인한 범위는 여기까지다.** 2026-10-07 실행은 **비정형(L0) 경로의
LLM 추출 응답 캐시**(`ocr_cache`) 한 가지를 공개 테스트 PDF 1건·청크 1건으로 재 것이다.
`gpt-4.1-mini-text` 1회 호출이었다.

- **Upstage 등 다른 OCR 제공자 경로는 이 실행으로 검증되지 않았다.** 정형 문서
  (`kepco_bill` 등)는 이 캐시를 지나지 않아 신규/재생이 갈리지 않는다.
- 1회 측정이므로 분포·절감률을 말하지 않는다. 두 전체 경과를 그대로 적었다.
- BM 실제 응답은 라벨 확정 전까지 열지 않으므로 ②의 실행 입력에도 쓰지 않았다.

## 5. 리허설 — 지금 시작하는 방법 (사람이 하는 부분)

**이것은 라벨 작성 시간이 아니다.** 라벨 초안을 만드는 시간과 섞지 않는다. 여기서 재는
것은 "**자료를 받아 응답서를 채우는 실사용 작업**"을 `manual` 회차와 `esgenie` 회차로
각각 수행한 시간이다.

### 5.1 준비물

| 항목 | 경로·내용 |
|---|---|
| 기록 양식 | `/private/tmp/esg_eval_timing/data/eval/worklog_template.csv` — **복사해서** `/private/tmp/esg_eval_timing/data/eval/worklog/<세션ID>.csv`로 쓴다. 템플릿 자체는 헤더만 둔 채 비워 둔다 |
| 참가자 식별자 | 지민이 정한다(`P1` 등). **이름을 임의로 넣지 않는다** |
| 문항 집합 | 두 회차에 **같은 집합**을 쓴다. 집합과 문항 수를 `note`에 적는다. 제안 집합은 §5.1.1 |
| 입력 | **저장소의 공개 테스트 문서 3건만** 쓴다 — `data/test_docs/kepco_bill_2025_12.pdf`, `waste_ledger_2025.pdf`, `safety_policy_2025.pdf`. **BM 원본 세트와 BM 실제 응답(LIVE)은 쓰지 않는다** |
| 시계 | 날짜가 보이는 시계. `start`/`end`는 **날짜+시각**으로 적는다 |

#### 5.1.1 제안 문항 집합 — 4문항 (양 회차 동일)

| qid | 문항 | 측정량·단위 |
|---|---|---|
| `RBA-C-8-E-4-1` | C-8 에너지 소비·온실가스 | **에너지 사용량 · TJ** |
| `RBA-C-4-E-6-1` | C-4 고형폐기물 | 폐기물 배출량 · 톤 |
| `RBA-C-4-E-6-2` | C-4 고형폐기물 | 폐기물 재활용(순환이용)률 · % |
| `RBA-E-11` | 문서·기록 관리 | 정성(`yes_no_evidence`) |

**`RBA-C-8-E-4-1`은 "에너지 사용량(TJ)" 문항이다.** 전에 "전력 사용량"이라고 안내한
것은 틀렸다 — **정정한다.** 사업장 전체 에너지 사용량을 **TJ로** 묻는 문항이고,
전력 사용량은 그 입력 중 하나일 뿐이다.

**이번 공개 샘플 입력에 전력 외 에너지원(가스 등) 자료가 있다고 전제하지 않는다.**
(2026-10-09 정정: 이전 문구는 가스 자료가 있다고 전제했다.) 작업자가 입력을 직접 보고
아래를 구분해 판단한다.

1. 입력에 실제로 들어 있는 에너지원은 무엇인가 (제공되지 않은 에너지원을 0이나
   "없음"으로 간주하지 않는다)
2. 자료에 적힌 단위를 TJ로 환산할 근거(계수)가 자료 또는 확인 가능한 출처에 있는가
3. 자료의 기간·사업장 범위가 "전체 사용량"을 덮는가, 일부인가

전체 사용량을 구성할 수 없거나 환산 근거가 없으면 값을 만들지 말고 `보완자료정리`
단계로 적고 넘어간다. 리허설에서 재는 것은 **작업 시간**이며 값의
정확성 판정이 아니다(§5.5).

집합을 바꾸고 싶으면 두 회차에 **같은** 집합을 쓰기만 하면 된다. 바꾼 집합을 `note`에
적는다.

#### 5.1.2 답안 저장 위치 — 시간 기록과 **다른 파일**이다

리허설에서 재는 것은 작업 시간이지만, 작업을 하려면 **채운 답을 둘 곳**이 필요하다.
시간 CSV에 답을 섞어 적지 않는다.

| 용도 | 경로 |
|---|---|
| **시간** | `data/eval/worklog/<세션ID>.csv` (양식 `data/eval/worklog_template.csv`) |
| **답안** | `data/eval/rehearsal_answers/<세션ID>.csv` (양식 `data/eval/rehearsal_answers_template.csv`) |

답안 양식의 열:

| 열 | 값 |
|---|---|
| `session_id`·`participant`·`method`·`request_round`·`qid` | 시간 CSV와 **같은 값**을 쓴다(두 파일을 이 키로 맞춘다) |
| `measure`·`unit` | §5.1.1 표의 측정량·단위 |
| `value` | 채운 값. **환산 계수·근거가 없어 못 채웠으면 비워 둔다** — 값을 만들지 않는다 |
| `evidence_doc` | 근거로 본 공개 테스트 PDF 파일명 |
| `evidence_locator` | 그 안의 위치(쪽·항목명). 자유 기술 |
| `needs_more_data` | 보완자료가 필요하면 `Y`, 아니면 비움 |
| `note` | 자유 기술 |

**두 양식 모두 헤더만 있고 예시 값이 없다.** 합성 값이 실제 기록으로 오인되지 않게
하기 위해서다. **AI가 답이나 시간을 채워 넣지 않는다.**

### 5.2 실제로 할 작업

1. **`manual` 회차** — 제품을 쓰지 않고 자료를 직접 읽어 응답서를 채운다.
2. **`esgenie` 회차** — 같은 문항 집합을 제품으로 처리하고, 생성된 실행 폴더 경로를
   그 회차 행들의 `run_dir`에 적는다.
3. 두 회차 모두 **단계가 바뀔 때마다 그 자리에서** `start`/`end`를 적는다. 끝난 뒤
   기억으로 채우지 않는다.

### 5.3 작업·대기·중단을 적는 방법

| 무엇 | 어떻게 적는가 |
|---|---|
| 사람이 손을 움직인 시간 | `step`을 `원문확인`·`값입력`·`수정`·`보완자료정리`·`출력` 중에서 골라 한 행 |
| 기계를 기다린 시간 | `step` = `처리대기`로 한 행. 기다리는 동안 다른 문항을 입력했다면 그 구간은 **작업 단계로도 적는다** — 집계가 대기에서 자동으로 뺀다 |
| 자리를 비운 중단·휴식 | **행을 적지 않는다.** 기록되지 않은 빈 시간은 집계에서 `idle_seconds`로 계산된다. 중단을 `처리대기`로 적지 않는다 |
| 끝 시각을 놓친 행 | `end`를 **비워 둔다.** `missing_end`로 걸리고 합산에서 빠진다. 추정해서 채우지 않는다 |

### 5.4 끝나고 돌려줄 것

1. 채운 CSV 파일(회차별로 한 파일이어도, 한 파일에 두 회차가 섞여 있어도 된다).
2. `esgenie` 회차의 실행 폴더 경로 목록.
3. 중간에 생긴 기록 누락·이상(예: 시계를 놓친 구간)을 `note`에 적은 그대로.

받으면 A가 아래 명령으로 검증·집계하고, 경고(`missing_end`·`negative_idle`·
`pipeline_exceeds_wait`)를 숨기지 않고 함께 보고한다.

```bash
python scripts/aggregate_worktime.py data/eval/worklog/*.csv \
  --read-run-dirs --out /tmp/worktime.json
```

**AI가 리허설 시간을 만들어 기록하지 않는다.** 현재 사람 리허설 기록은 **0건**이고,
테스트·안내에 나오는 시각은 모두 합성 값이라고 해당 파일에 적어 두었다. 참가자와 실제
시간은 사람이 적는다.

### 5.5 이 리허설이 완료시키는 것과 완료시키지 않는 것

**두 트랙을 한 칸에 적지 않는다.**

| 트랙 | 입력 | 완료 조건 | 현재 상태 (2026-10-07) |
|---|---|---|---|
| **공개 샘플 리허설**(이 §5) | 저장소 공개 테스트 PDF 3건 | 두 회차 CSV + 실행 폴더 경로 수령 → 집계·경고 보고 | **미실시** — 빈 세션 파일만 있다 |
| **새 BM 세트의 실제 시간 비교** | 한울정밀 보강 세트 | 라벨 확정 + B 독립 검토·형식 합의·새 실행 ID가 모두 확인된 뒤 | **시작 전** |
| **BM 정답 라벨 확정** | 한울정밀 보강 세트(원본 증빙) | 라벨 확정 + 선행 커밋·SHA + B 독립 검토 + 형식 합의 | **A 쪽 확정은 비공개 로컬 브랜치에서 완료**, B 독립 검토·형식 합의·새 실행 ID는 **대기** |

**공개 샘플 리허설 기록을 새 BM 세트의 실제 시간 비교와 같은 파일·같은 집계에 넣지
않는다.** 두 트랙은 입력 자료가 다르다(공개 테스트 PDF 3건 ↔ 한울정밀 보강 세트).
세션 ID와 `note`에 어느 트랙인지 적어 구분한다 — 공개 샘플은 `리허설01`처럼 적고,
