### 2. "채점 규칙이 boundary를 실제로 쓰는지" — 안 씁니다

코드를 확인했습니다.

- 채점기의 응답 자료구조(`SystemAnswer`)에 **boundary 필드가 없습니다.** 공통 형식
  검증기는 `boundary`의 키 이름·자료형만 보고, 채점에는 넘기지 않습니다.
- 근거 일치는 **(파일명, 쪽)** 집합의 교집합으로만 판정합니다. 인용문(`quote`)도 비교하지
  않습니다.
- 따라서 boundary 2칸을 비우셔도(`null`) 채점 결과는 달라지지 않습니다.

**다만 이것은 한계입니다.** 기간·사업장·분모가 어긋난 응답을 채점기가 **자동으로 잡지
못한다**는 뜻입니다. 사람 라벨의 `boundary_note`에 범위를 적어 두면 사후 검토에서
발견할 근거가 되지만, **사람 라벨이 모든 범위 오류를 자동으로 잡아 준다고 보장할 수
없습니다.** 지금은 "자동 비교 없음 + 수동 검토 단서"가 전부입니다. 자동 비교를 넣을지는
별도 결정 사항으로 남깁니다.

### 3. 자료 성격 표기 — 수정 요청

가상 자료인지 공개 보고서인지 실제 기업 자료인지는 **구조화된 필드**로 두는 것을
제안합니다. `meta.notice`의 첫 토큰에 넣으면 사람이 읽는 안내문에 섞여 가려지고,
기계로 거를 수도 없습니다. 세트 설명·`stage`와도 섞이지 않게 분리합니다.

```json
"meta": {
  "material_kind": "fictional",      // fictional | public_report | real_company (필수, 1개)
  "material_note": "한울정밀 촬영세트 BM개편 20260928",  // 세트 설명. 성격 판단에 쓰지 않는다
  "stage": "initial"                  // 단계. 성격과 무관
}
```

지금 받은 원본 세트는 구성 목록에 `fictional: true`로 적혀 있어 `fictional`에
해당합니다. 이 필드명과 값 3종으로 괜찮은지 확인 부탁드립니다.

### 4. 대조군 판정 선택지 — '확정'과 '응답'이 실제로 무엇이 다른가

제안했던 '확정' 명칭을 먼저 설명하겠습니다.

| 선택지 | 뜻 | 채점 처리 |
|---|---|---|
| `confirmed` (확정) | 값과 **근거 위치(파일·쪽)** 를 함께 제출한 응답 | 자동응답률 분자에 들어간다 |
| `unverified_submitted` (미검증 제출) | 값은 냈지만 근거 위치가 없거나 자가주장만 있는 응답 | **분자에 넣지 않는다** |

즉 두 선택지를 가르는 것은 **근거 위치를 함께 냈는지**뿐입니다.

**명칭을 바꿔서 두 시스템의 검증 수준이 같아지는 것은 아닙니다.** `confirmed`는
"시스템이 근거를 붙여 냈다"는 뜻이고, "그 근거가 맞다"는 뜻이 아닙니다. 근거가 정답
위치와 맞는지는 라벨과 대조해 **따로** 셉니다. 그래서 자동응답률(M4)을 **'검증 확정률'
이라고 부르지 않습니다** — 아래 5번.

B가 쓰시던 '응답' 선택지를 그대로 두고 분자 조건만 맞추는 방법도 괜찮습니다. 어느
쪽이든 **근거 위치 제출 여부로 나뉜다**는 점만 같으면 됩니다. 선호를 알려주세요.

### 5. 지표 이름 정정 — M4는 '검증 확정률'이 아닙니다

| 지표 | 정의 |
|---|---|
| **M4 자동응답률** | 분모: 실행·단계별 예상 문항 전체 48행 / 분자: `confirmed` 로 제출한 행 |

**근거 검증이 완료된 비율이 아닙니다.** 특히 대조군에서는 "검증 확정"을 뜻하지
않습니다. `confirmed` + `unverified_submitted`를 합친 값 제출률은 **별도 보조 수치**로만
냅니다. 1차 회신 초안에서 '검증 확정률'이라고 쓴 것을 정정합니다.

근거 일치는 의견 주신 대로 **파일 일치 / 파일+쪽 일치 2단계**로 나눕니다. 공식 수치는
**파일+쪽**이고, 파일 일치는 공식을 대체하지 않는 보조입니다.

### 6. 라벨링 기준 질문 2건

**(1) 예/아니오 문항의 `expected_value`**

`예` 또는 `아니오`를 적어 주세요. 채점기가 토큰을 정규화합니다:
`예`/`y`/`yes`/`true` ↔ `아니오`/`아니요`/`n`/`no`/`false`. **`0`·`1`은 예/아니오로
해석하지 않습니다**(수치로 봅니다). 빈칸은 `answer` 행에서 오류입니다.

**(2) 단위 환산이 필요한 경우 — `answer`인가 `hold`인가**

둘로 나뉩니다. **모두 `not_comparable`로 묶지 말아 주세요.**

| 상황 | 판정 |
|---|---|
| 같은 측정량·기간·대상이고 **환산 계수가 자료에 있거나 정의상 자명**(kg↔톤, kWh↔MWh 등) | **`answer`** — 문항 요구 단위로 환산해 적고 `boundary_note`에 환산 근거를 적는다 |
| 환산에 **자료에 없는 계수**가 필요(발열량, 배출계수 등) | **`hold` / `not_comparable`** |
| 환산은 되지만 **기간·대상이 문항과 다르다**(월 값 ↔ 연간 요구) | **`hold` / `not_comparable`** |
| 자료 자체가 **없다** | **`hold` / `no_evidence`** — `not_comparable`로 적지 않는다 |
| 기간·대상·분모가 **불명확해 판단이 안 선다** | **사람 확인 대상으로 남겨 주세요.** `note`에 이유를 적고 넘겨 주시면 됩니다. 임의로 `not_comparable`에 넣지 않습니다 |

`not_comparable`은 "비교 기준이 어긋남"이고 `no_evidence`는 "자료 없음"입니다. 둘을
합치면 나중에 원인을 구분할 수 없습니다.

**(3) 추가 — `answer` 행의 `expected_sources`는 필수입니다**

`answer` 라벨에는 `파일명#페이지`(1-기준, 여러 개는 `;`)를 반드시 적어 주세요. 비면
채점기가 **라벨 검증 오류**로 거부합니다. 비어 있는 행을 지표 분모에서 빼면 그만큼
수치가 높아지기 때문에, 조용히 넘기지 않도록 바꿨습니다. `hold`·`na`에는 필요 없습니다.

#### 9.3 수정안을 다시 확인해야 하는 항목 — **A가 안을 바꿨습니다**

아래 2건은 B가 이미 수정 의견을 주셨고, 그 뒤 **작업지시서 §4 원문(공통 답안 형식

명세 필드에 옮기는 형태로 다시 올립니다.

| # | 항목 | 지금까지 나온 안 | A의 새 안 |
|---|---|---|---|
| **I-2** | 데이터 출처 표현 | A 1차: `meta.data_source` 자유 문자열 / B 수정 의견: `meta.material_kind` 구조화 enum(`fictional`·`public_report`·`real_company`) + 설명은 `material_note`로 분리 | **두 축을 나눕니다.** ⓐ **자료 성격**은 명세가 정한 `dataset_tag` 필수 enum — `virtual` / `public_report` / `real_pilot`. B가 제안한 구조화·분리 취지와 같고 값 3종도 1:1 대응합니다(`fictional`→`virtual`, `real_company`→`real_pilot`). ⓑ **입력 자료 구성**(증빙 12건인가 +보완 1건인가)은 성격과 **다른 축**이라 별도 필드가 필요합니다. 이번 세트는 `dataset_tag="virtual"` + 자료 구성 문자열입니다 |
| **I-3** | 대조군 판정 구조 | A 1차: `decision` **6개 값**(`confirmed`/`unverified_submitted`/`hold`/`not_applicable`/`unparsed`/`undetermined`) + 판정 기준 5줄 / B 의견: '확정' 명칭 대신 '응답'을 쓰고 분자 조건만 맞추자 | **명세는 `decision` 3개 값(`answer`/`hold`/`na`) + `decision_detail`(원 status/comparison) 구조입니다.** A의 6개 값과 **모양이 다릅니다.** 어느 구조로 갈지는 A가 혼자 정할 수 없어 지민 결정 + B 재확인 사항으로 올립니다 |

**I-3에서 반드시 보존해야 하는 것**(어느 구조를 택하든 바뀌지 않습니다):

- **미검증 제출을 확정 응답으로 세지 않습니다.** 3값 구조로 가면 `answer` 안에
  미검증 제출이 섞이므로, `decision_detail`로 **반드시 갈라낼 수 있어야** 합니다.
  갈라낼 수 없으면 자동응답률 분자가 부풀어 오릅니다.
- **파싱 실패를 보류로 바꾸지 않습니다.** 3값에는 `unparsed`에 대응하는 값이 없어
  이 자리를 어디에 둘지 함께 정해야 합니다. `hold`로 흡수하면 올바른 보류로 잘못
  셉니다.
- **규칙이 없는 조합을 임의 배정하지 않습니다**(`undetermined` 자리). 없애면
  `unresolved`로 드러날 길이 막힙니다.

**공통 형식 전체는 아직 확정이 아닙니다.** `format_version`은 `1.0-draft`를 유지합니다.

**선택적 후속 개선안 (지금 필수 산출물을 막지 않습니다)**

공통 형식에는 **시스템의 보류 사유를 담는 구조화 필드가 없습니다.** `decision_basis`는
자유 서술이고, `source.comparison`(`compared`/`mismatch`/`not_comparable`/
`scope_unconfirmed`)에는 라벨의 `no_evidence`·`needs_human_text`에 대응하는 값이
없습니다.

- 그래서 `hold × hold` 행의 **보류 결정**은 집계하되 **사유**는 `hold_reason_unknown`
  으로 남깁니다. **미확인을 사유 일치로 세지 않습니다.**
- **자유 서술에서 사유를 추정해 일치로 처리하지 않습니다.**
- 기존 형식에서 사유를 확인할 수 없으면 그대로 `hold_reason_unknown`입니다. 이것은
  정상 동작이며 산출물 완성을 막지 않습니다.
- 구조화 필드 추가는 **선택적 후속 개선안**입니다. B 합의 없이 넣지 않고, 넣게 되면
  부 버전을 올립니다(형식 문서 §7).

**남은 것**

- **I-2·I-3의 재확인**(§9.3). 자료 성격 필드(3번)는 I-2로, 대조군 판정 선택지(4번)는
  I-3으로 합쳐 봅니다. I-3은 지민 결정이 먼저 필요합니다.
- **I-4의 조건 확인**(§9.2). A의 답이 조건과 맞는지만 알려 주시면 됩니다.
- 행별 집계 판정표는 2026-10-06 **확정**됐습니다
  (`docs/지표결정요청표_2026-10-06.md` §6.2). 판정표 **이전 단계**의 미정은 §6.3에
  적었고 `unresolved`로 남깁니다.
- 프롬프트 최종 고정과 본 실행은 **공통 형식 합의 이후**입니다.
- `final` 패키지는 확정 라벨이 없어 만들지 않았습니다.
