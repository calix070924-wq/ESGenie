# 작업 0 — OCR 비결정성 조사 (캐시 설계 근거)

2026-07-27 · `feature/ocr-cache` (부모: `feature/l1-node-selection`, 미머지 스택)
후속: `docs/OCR캐시_결과_2026-07-27.md`

## 결론 먼저

**비결정 지점은 딱 한 곳이다 — `_extract_unstructured_text`의 LLM 호출.**
그 앞단(pymupdf 텍스트 추출 → 행 복원 → 청킹)은 **바이트 단위로 결정적**이고,
그 뒷단(`_map_vlm_json` → `_augment_unstructured_clauses` → `_backfill_kesg_codes`)도
순수 함수다. 즉 **LLM 응답 하나만 고정하면 파이프라인 전체가 재현된다.**

측정으로 확인했다: 같은 PDF에 `_extract_text_pymupdf`를 5회 돌려 SHA256이 5/5 동일.
그래서 캐시 키는 **"LLM에 실제로 들어간 입력 문자열"의 해시**로 잡는다(작업 1).
입력이 결정적이므로 키가 흔들리지 않고, 전처리를 고치면 입력이 바뀌므로 키가 자동 무효화된다.

주의: **캐싱은 OCR을 결정적으로 만드는 게 아니다.** LLM은 여전히 비결정적이다.
목표는 검증 루프에서 **OCR 변동을 상수로 고정**해, 규칙 변경의 효과와 추출 변동을 분리하는 것이다.

## 2. 비결정 지점 특정 — 어디가 LLM이고 어디가 결정적인가

`extract_document` → `extract_unstructured` 경로를 단계별로 갈랐다.
(현대모비스 지속가능경영보고서는 라우터가 비정형으로 보내므로 이 경로가 전부다.)

| # | 단계 | 위치 | 성질 | 실행 간 변동 |
|---|---|---|---|---|
| 1 | 라우팅 판정 | `route_document` → `_quick_preview` / `estimate_layout_features` | 결정적(규칙+pymupdf) | 없음 — 키워드 점수·표비율은 파일만의 함수 |
| 2 | PDF 텍스트 추출 | `_extract_text_pymupdf` (`max_pages=300`) | **결정적(라이브러리)** | **없음 — 5회 SHA256 동일(§3)** |
| 2a | 좌표 기반 행 복원 | `_reconstruct_rows_from_dict` + `_inherit_label_rows` + `_attach_column_headers` | 결정적(순수 계산) | 없음. **단 코드를 고치면 출력이 바뀐다** → 캐시 키가 반응해야 하는 지점 |
| 3 | 스캔본 폴백 OCR | `_call_upstage_dp(ocr_mode="force")` | **외부 API — 비결정 가능** | 있음(모델 버전·서버측 갱신). 현대모비스는 임베딩 텍스트가 있어 **이 경로를 타지 않는다** |
| 4 | 청킹 | `_split_text_chunks(raw_text, 4000)` | 결정적(순수 함수) | 없음 — 341,184자 → 87청크 재현(§3) |
| 5 | **LLM 추출** | `_extract_unstructured_text` → `LLMClient.complete(temperature=0.0, json_mode=True)` | **LLM — 비결정** | **있음. §1의 모든 차이가 여기서 나온다** |
| 6 | JSON 파싱·매핑 | `re.search(r'\{.*\}')` → `_map_vlm_json` (+ G6 각주 배제) | 결정적 | 없음 — 입력 응답이 같으면 같은 결과 |
| 7 | 존재형 조항 보강 | `_augment_unstructured_clauses` | 결정적(키워드) | 없음 |
| 8 | 코드 backfill | `_backfill_kesg_codes` (`taken_by_label` 가드) | 결정적(사전) | 없음 |
| — | 미사용 | `_render_pages_b64` | — | **현재 어떤 호출부도 없다**(저장소 전역 grep 확인). 비전 채널 잔존 헬퍼라 비결정성 논의 대상이 아니다 |

정리하면 **비결정 = 5번(항상) + 3번(스캔본일 때만)** 이다. `temperature=0.0`은
결정성을 보장하지 않는다 — 서버측 배치·커널·모델 스냅샷 차이로 토큰이 갈린다.

한 가지 더: 4번의 청킹 파라미터(`_UNSTRUCTURED_CHUNK_CHARS=4000`)가 바뀌면 5번의 입력이
전부 재분할된다. 그래서 캐시는 **청크 단위**로 키를 잡는다 — 청킹이 바뀌면 87개 키가 전부
새 키가 되어 자동 무효화된다(작업 1).

### 2-1. 캐시 대상 경계

캐시가 담는 것은 **5번의 응답(청크별 metrics/clauses)** 이다. 6·7·8번은 캐시 밖에서
항상 재실행된다. 특히 `_backfill_kesg_codes`는 `extract_document`의 전 채널 합류점이고
사전이 갱신되면 결과가 달라져야 하므로, **캐시는 그 이전 산출물만 담는다.**

## 3. pymupdf 결정성 검증 — 측정값

여기가 흔들리면 키 설계가 달라진다(입력 문자열을 키로 쓸 수 없다). 그래서 먼저 쟀다.

```bash
# 오프라인. LLM 호출 없음.
python3 - <<'EOF'
from esgenie.ssot.ocr_router import _extract_text_pymupdf, _split_text_chunks, \
    _UNSTRUCTURED_MAX_PAGES, _UNSTRUCTURED_CHUNK_CHARS
import hashlib
for i in range(5):
    t = _extract_text_pymupdf("data/real_reports/012330_mobis_2025.pdf",
                              max_pages=_UNSTRUCTURED_MAX_PAGES)
    print(len(t), len(_split_text_chunks(t, _UNSTRUCTURED_CHUNK_CHARS)),
          hashlib.sha256(t.encode()).hexdigest())
EOF
```

결과 (PyMuPDF 1.27.2.3 / MuPDF 1.27.2, Python 3.13, darwin):

```
341184  87  0fe648f66ca8802d432b7b9657870bc384bdba750b6e6b734fa8760c6b33dbc9
341184  87  0fe648f66ca8802d432b7b9657870bc384bdba750b6e6b734fa8760c6b33dbc9
341184  87  0fe648f66ca8802d432b7b9657870bc384bdba750b6e6b734fa8760c6b33dbc9
341184  87  0fe648f66ca8802d432b7b9657870bc384bdba750b6e6b734fa8760c6b33dbc9
341184  87  0fe648f66ca8802d432b7b9657870bc384bdba750b6e6b734fa8760c6b33dbc9
```

**5/5 바이트 동일.** 341,184자, 87청크. 행 복원(`_reconstruct_rows_from_dict`)과
청킹까지 포함해 결정적이다.

→ **키 설계 확정**: `sha256(모델명 + 프롬프트 전문 + doc_type + LLM 입력 텍스트)`.
입력 텍스트가 결정적이므로 같은 PDF·같은 코드 = 같은 키. 전처리를 고치면 입력 텍스트가
바뀌므로 키가 저절로 달라진다.

pymupdf **버전**이 바뀌면 추출 텍스트가 바뀔 수 있는데, 그때도 키가 따라 바뀌므로
캐시가 낡은 값을 돌려주지 않는다. 버전 문자열을 키에 넣지 않아도 되는 이유다.

## 4. 도구 — `scripts/ocr_diff.py`

§1-2·1-3의 출력을 낸 도구다. 두 `ledger_provenance_*.json`을 받아 비교한다.

```bash
python3 scripts/ocr_diff.py outputs/ledger_provenance_012330_v2.json \
                            outputs/ledger_provenance_012330_v3.json --show 4
python3 scripts/ocr_diff.py a.json b.json --codes E-4-1 E-6-1   # 코드 한정
```

| 출력 | 의미 |
|---|---|
| 코드별 노드 수 / hint 수 / 공통·소실·신규 / 자카드 | 추출 변동의 폭 |
| hint 변화 상세 | 라벨 문자열이 어떻게 바뀌었는지(선택 규칙 어휘 매칭 영향 판정용) |
| 같은 hint · 값 변화 | 라벨은 같은데 값·연도가 달라진 것 = 표 파싱 변동 |
| `판정` | `완전 동일 — 재현됨` / `차이 있음 — 추출이 흔들렸다` |

**§1의 v2 vs v3 출력이 기준선이다.** 캐시가 작동하면 같은 캐시를 쓴 두 실행의
`판정`이 `완전 동일 — 재현됨`, `hint 공통 비율 100.0%`, `Δ0`으로 나와야 한다.
48.1% → 100%가 이 트랙의 성공 조건이다.

## 5. 캐시가 하지 않는 일

| 착각 | 사실 |
|---|---|
| 캐시가 OCR을 결정적으로 만든다 | **아니다.** 캐시 미스일 때의 LLM 호출은 여전히 비결정적이다. 같은 키로 두 번째부터만 같은 값이 나온다 |
| 캐시가 추출 정확도를 올린다 | **아니다.** 틀린 추출을 고정할 뿐이다. E-4-2가 10.0%로 굳으면 10.0%가 재현된다 — 재현은 되지만 여전히 오답이다 |
| 캐시가 있으면 라이브를 안 봐도 된다 | 아니다. 오프라인 리플레이는 라이브를 보장하지 않는다. 캐시는 **라이브를 1회로 줄이는** 장치다 |

정확도 문제(E-4-2 동률 tie-breaker, E-4-1 추출 누락, (나) 연도 열 뭉개짐)는 이 트랙 범위 밖이다.
다만 **캐시가 있어야 그 작업들이 검증 가능해진다** — 규칙을 바꿨을 때 값이 변한 원인이
규칙인지 추출인지 갈릴 수 있기 때문이다.
