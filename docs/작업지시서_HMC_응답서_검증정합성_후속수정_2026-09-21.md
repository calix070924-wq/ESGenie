### 2-1. 실제 기간을 비교 가능한 형태로 보존

- 월간/연간과 개월 수 외에 해당 연도·월 또는 확인된 시작일·종료일을 보존한다. 필요한 최소 필드를 기존 경계 모델에 추가하고 기존 JSON 읽기 호환성을 유지한다.

- 같은 기간의 다른 표기는 정규화하여 같은 것으로 비교할 수 있게 한다. 날짜 범위가 있다고 무조건 한 달로 읽지 않는다. 연간 날짜 범위와 월간 고지서 범위를 각각 검증한다.

- 현재 행·열의 명시된 측정 대상과 범위를 우선한다. 문서 제목·머리말은 부족한 축을 보완하는 데 사용한다.

## 작업 3. 합산의 중복·기간·범위 조건 수정 — F1·F2

우선 볼 파일: `esgenie/ssot/boundary.py`의 `plan_sum`, `selection.py`의 합산·원장 확정 경로, `ssot_pipeline.py`.

### 3-1. 총량과 구성요소의 포함 관계를 처리

- 같은 계열 문자열인지 외에 실제 포함 관계를 판단한다. 전체 에너지는 전력과 연료를 포함하고, 전력 총량은 해당 전력 구성요소를 포함한다.
- 같은 기간·범위의 신뢰할 수 있는 총에너지 10 TJ와 전력 6 TJ·가스 4 TJ가 함께 있으면 10 TJ를 보존한다. 세 값을 20 TJ로 합산하지 않는다.
- 총량 후보라는 이름만으로 우선하지 않는다. 실적·범위·단위·대표값 자격이 확인된 총량인지 검증한다. 목표 총량이나 다른 사업장 총량이 정당한 구성요소를 밀어내면 안 된다.
- 총계+소계+세부항목, 동일 고지서 중복, 단위만 다른 같은 값, 가스 m³와 MJ의 중복을 막는다. 조달수단과 실물 사용량이 같은 에너지를 중복 표현하는 경우도 확인 없이 더하지 않는다.
- 서로 다른 값의 독립 증빙을 ‘같은 측정 대상’이라는 이유로 중복 업로드로 처리하지 않는다. 중복 제거와 불일치 검토를 구분한다.

### 3-2. 합산에 필요한 조건을 먼저 확인

- 실제 기간이 같고, 합산할 수 있는 사업장 경계이며, 중복되지 않는 실측 에너지원임이 확인될 때만 합산한다.
- 다른 달이나 다른 해는 합산하지 않는다. 기간·사업장이 미상이면 확인된 동기간·동범위 합으로 만들지 않는다.
- 사업장 이름이 다르다는 이유만으로 무조건 부적합하게 처리하지 않는다. 공장 전체 전력과 그 공장 내 특정 라인의 가스처럼 포함 관계가 입증된 경우 제한된 부분합을 허용할 수 있다. 사용한 범위와 남은 부족 사유를 명시한다.
- 합산이 불가능한 경우 잘못된 합을 남기고 배지만 낮추지 않는다. 적절한 단독 참고값 또는 미확정 상태와 구체적 보완 사유를 남긴다.
- 공용 단위 변환, 채택 근거, 제외 근거와 산식을 보존한다. 가스 체적만 있으면 확인되지 않은 열량계수를 적용하지 않는다.
- 합산을 결정하는 곳과 확정 원장이 같은 결정을 소비하게 한다. 순서·중복 업로드에 따라 값·근거·상태가 달라지지 않아야 한다.

정상 기준: 동일한 실제 사용기간의 전기 142,560 kWh = 0.513216 TJ, 가스 360,772 MJ = 0.360772 TJ, 제한적 합 = **0.873988 TJ**. 이 합은 확인한 기간·사업장의 두 에너지원 합이며, 전사 연간 총량의 증명은 아니다.

### 5-1. 비교 가능성을 먼저 판단

처리 순서는 **비교할 지표와 범위 확인 → 단위 정규화 → 비교 가능한 값의 오차 계산 → 상태와 사유 전달**이어야 한다.

- 부분값과 전체 주장, 다른 달, 다른 사업장, 다른 분모를 숫자 차이만으로 실제 불일치라고 확정하지 않는다. 명확히 다른 대상과 필요한 경계가 미상인 상황을 구분한다.
- 부분값 10.6%와 전체 주장 92%의 경우 차이가 크더라도 동일 범위가 입증되지 않았다면 `mismatch`로 확정하지 않는다.
- 필요한 범위가 미상인 경우 계산하지 못했다는 상태와 사유를 남긴다. 비교하지 않은 항목이 위험 0·대조 완료·verified처럼 표시되지 않게 기존 D1 평가 상태 계약을 유지한다.
- 조건이 동일한 142,560 kWh와 142.56 MWh는 일치해야 한다. 동일 조건의 과대·과소 주장은 계속 양방향 탐지한다.
- 기존 D1 가중치와 오차 임계값, 공급망 비율 10%p를 변경해서 범위 오류를 가리지 않는다. 비교 자격을 먼저 바로잡는다.

### 5-2. origin 대신 독립 문서 여부를 판단

- 동일 `ocr_structured` 또는 동일 `ocr_unstructured`여도 서로 독립된 문서는 비교할 수 있어야 한다.
- 같은 공장·같은 사용기간의 독립 PDF 두 장에 100 kWh와 200 kWh가 있으면 실제 불일치를 전달한다.
- 동일 원문 재추출·중복 업로드는 독립 검증 근거로 세지 않는다. 파일명만 다른 복사본과 내용이 다른 독립 문서를 구분하는 데 기존 식별자·해시·원문 출처 정보를 우선 활용한다.
- 관계없는 기간·사업장 문서가 추가됐다고 기존의 충분한 대표값을 무조건 강등하거나 경고를 쏟지 않는다. 채택값의 검증에 영향을 주는 비교와 참고 비교를 구분한다.

### 5-3. 상위 판정과 담당자 할 일을 보존

- 상위에서 확인한 실제 불일치를 하위의 숫자 일치·부분값 처리로 덮지 않는다. 비교 상태뿐 아니라 해당 사유·근거도 보존한다.
- 여러 비교에서 나온 결과는 그 비교 대상과 함께 보존한다. 한 쌍의 ‘비교 불가’가 다른 독립 증빙 간 ‘실제 불일치’를 지우면 안 된다.
- `scope_unconfirmed` 및 요구 범위 부족으로 검증을 보류한 답변은 제출 전 체크리스트에 ‘범위 확인·보완’ 등 실행 가능한 항목으로 나타나야 한다. `self_reported`라는 배지만으로 완료 항목처럼 제외하지 않는다.
- 무엇을 확인할지 구체적으로 적는다. 예: 사용기간, 전사/공장 범위, 총전력/총에너지 분모, 기존 설비 여부, 중복 증빙의 원문 동일성.
- UI·JSON·Excel·PDF·체크리스트가 같은 판정과 사유를 소비해야 한다. 모든 estimated나 관련 없는 참고값을 일괄 flagged로 바꾸지 않는다.

## 작업 6. E-7/E-8의 근거 선별과 초안 조건 보완

우선 볼 파일: `supplychain/question_fitness.py`, `drafter.py`, 기존 검색·grounding·승인 게이트.

현재 E-7은 좋은 의사소통 근거가 함께 있을 때 무관한 문서를 잘 줄인다. 그러나 정보보호 문서만 있으면 통과할 수 있고, E-8은 10개 문서 중 6개를 남기며 정보보호·근로시간·위생 문서까지 포함한다. 이 동작을 개선하라.

- 같은 문서를 단독·혼합·순서 변경으로 넣어 평가한다. 좋은 후보가 없어서 상대 하한이 낮아졌다는 이유로 무관한 문서가 근거가 되어서는 안 된다.
- E-7은 누구에게 어떤 경로로 방침·관행·기대·성과를 전달하는지, E-8은 근로자·이해관계자 참여·양방향 소통·구제 접근을 다룬다는 차이를 반영한다.
- `대표이사` 서명란, 지나가는 `고객·공급사·접근·보장` 같은 어휘만으로 질문에 답하는 근거로 인정하지 않는다. 반대로 정당한 고충처리 문서를 함께 차단하는 수치 하한 변경으로 해결하지 않는다.
- 문서 빈도, 문장/청크 수준의 관계, 기존 검색 특징, 필요한 경우 기존 관련성 게이트 등 구현 대안을 비교해 최소한의 효과적인 수정을 선택한다. 증빙 말뭉치 빈도가 유일한 해법이라는 전제로 전체 L0 개편을 선행시키지 않는다.
- 특정 파일명·노드 ID·시연 기업·고정 문장 화이트리스트나 무관 단어 목록으로만 해결하지 않는다. 코드 일치와 검색 폴백 모두 문항 적합성 조건을 만족해야 한다.
- 일부 측면만 뒷받침하는 근거는 확인된 내용에 한정된 초안으로 사용하거나 부족 상태로 유지한다. 공급사·고객·주기·담당자·인증 취득을 지어내지 않는다.
- 근거 있는 문장인지 확인하는 grounding과 질문에 답하는지 확인하는 적합성을 각각 검증한다. 관련성 테스트에서 grounding을 무조건 ACCEPT로 고정한 결과를 전체 초안 안전성의 검증으로 보고하지 않는다.

실제 문서에는 관련/부분 관련/무관 판정을 원문 인용과 함께 기록하고 다음 대조군을 둔다.

| 입력 | 요구 결과 |
|---|---|
| 실제 의사소통절차서 단독 | E-7에 확인된 범위의 초안 허용 |
| 정보보호 문서 단독 | E-7 소통 프로세스·E-8 참여/구제 근거로 부적절한 초안 생성 방지 |
| 고충처리·신원보호 문서 | E-8의 관련 근거 유지 |
| 위생·근로시간 등 인접 주제만 있음 | 근거에 없는 참여/구제 프로세스가 승인 대기 초안으로 나오지 않음 |
| 실제 10개 문서 혼합 및 순서 변경 | 관련 근거 보존, 무관 청크 제거, 순서에 따른 임의 변화 없음 |
| HMC 외 대표 문항과 동의어·복합어 표현 | 과도한 재현율 손실을 확인하고 보완 |

6양식 222문항의 ‘고유 어휘 존재’ 검사는 구조 점검으로 유지할 수 있다. 정확도·재현율 검증과는 구분하고, 사람이 라벨링하지 않은 모든 쌍을 ‘전수 오탐’이라고 단정하지 않는다.

라이브 LLM 호출은 이 작업의 필수 조건이 아니다. 결정적 회귀와 실제 원문 재생을 우선한다. 실제 호출을 하지 않았다면 생성 품질이 라이브 검증됐다고 표현하지 않는다. 라이브 호출을 한다면 기존 설정·권한 범위에서 수행하고 호출 범위·비용·모델·평가 결과를 mock과 분리해 기록한다.

## 작업 7. 원문 모순·ISMS·문항 안내의 미해결 사항 처리

### 7-1. 12번 문서의 실적/계획 충돌

- `12_재생에너지사용현황_2026-06.pdf`를 실패 회귀 원본으로 보존한다.
- 상반기 태양광 사용 실적과 하반기 착공 계획이 함께 있을 때, 별도의 기존 설비가 있다고 추정해서 해소하지 않는다. 동일 설비인지 확인되지 않았다는 사유를 원문 위치와 함께 남긴다.
- ‘상반기 값이므로 연간 전체성 부족’과 ‘실적/계획 또는 설비 동일성 확인 필요’를 각각 표현하고 체크리스트까지 전달한다.
- 정상 대조군은 별도 합성 자료로 만든다. 동일 설비의 모순, 명시된 서로 다른 설비, 충돌이 없는 정상 연간 실적을 구분한다. 숫자 10.6%나 파일명으로 분기하지 않는다.

### 7-2. 기존 ISMS 취득 문구 정정

- 18번 정보보호정책은 ‘인증 준비’와 ‘2026년 하반기 신청 예정’을 적는다. ‘ISMS 인증 취득’으로 쓰인 기존 응답서·보고의 위치를 확인한다.
- 원본 정책 PDF를 바꾸지 않는다. 확인된 잘못된 산출물은 새 정정본을 만들고, 기존 파일의 경로·해시·잘못된 문구·정정 문구·정정본 경로를 기록한다. 기존 산출물을 몰래 덮어쓰지 않는다.
- 정정은 ‘준비 중/신청 예정’이라는 사실을 정확히 옮기거나, E-7처럼 질문과 무관한 경우 해당 문장을 제외한다. 사람이 정정한 문구는 새 LLM 생성 결과처럼 보고하지 않는다.
- 어떤 기존 파일에 해당 문장이 있는지 확인할 수 없으면 찾은 범위와 미확인 대상을 명시한다. 실제 정정 없이 정정 완료라고 기록하지 않는다.

### 7-3. 존재하지 않는 문항 안내와 호환성

- C-7이 존재하지 않는 별도 수치 문항을 안내하는 문제를 수정한다. 현재 양식에 맞게 증빙 안내를 고치는 최소 수정부터 적용한다. 검증 오류를 고치기 위해 양식 문항 수를 불필요하게 늘리지 않는다.
- C-2의 실제 문구도 확인하되, 없는 오류를 전제로 바꾸지 않는다. 결과 보고의 C-2/C-7 설명을 실제 구현과 맞춘다.
- C-5의 기존 numeric qid와 새 존재형/수치형 문항 간 호환성을 점검한다. 저장 답변 재사용·초안 캐시·UI 캐시의 실제 소비 경로에서 예전 수치가 예/아니오로 재해석되지 않게 이관·무효화 또는 명확한 재작성 처리를 한다. 해당 소비 경로가 없다면 없는 경로를 만들지 말고 조사 결과를 기록한다.

## 작업 8. 실제 원장부터 산출물까지 검증 경로 재구성 — F4·F5

우선 볼 파일: `scripts/hmc_integrity_validation.py`, 실제 OCR·원장·응답 생성 진입점, exporter와 출력 테스트.

### 8-1. 검증 입력의 출처와 실행 단계를 구분

주요 검증은 다음 경로를 연결해야 한다.

`출처가 명확한 입력 → 경계 추출 → EvidenceGraph → 확정 원장 → D1 평가 → DataPoint → ResponseSheet → JSON/Excel/PDF/체크리스트`

- 기존 `demo_hmc_sheet.py`의 DATA_POINTS/MAPPED를 가져와 검증 엔진을 우회하지 않는다. 0.873988이나 검증 상태를 기대값에 맞춰 Answer에 직접 넣지 않는다.
- 실제 원문의 로컬 파서 경로가 있으면 그것을 사용한다. 저장 OCR 캐시는 실제 파일과 연결되는 것이 확인될 때만 사용한다. 없거나 다른 문서의 캐시면 없다고 기록한다.
- 실제 추출 입력을 확보할 수 없는 부분은 원문에서 수동 재구성한 입력임을 명시하고 원문 위치·추출 필드·실행 시작 단계를 기록한다. 재구성 입력을 실제 OCR 전체 재생이라고 부르지 않는다.
- 입력 PDF·캐시·fixture의 경로, sha256, 사용 페이지, 실제 사용기간을 기록한다. 파일을 읽은 사실과 그 파일이 실제 계산에 사용된 사실을 구분한다.
- 정상 합산 사례, 부분/미상/충돌 사례, 실제 불일치 사례를 각각 새 출력에 포함한다. 필수 사례가 실제 입력 조건 때문에 보류된다면 보류가 정답이며, 별도의 출처가 명확한 통제 실험에서 정상 값을 검증한다.

### 8-2. 검사 누락과 빈 대상 통과를 실패로 처리

- 잘못된 폐기물 qid `HMC-C-4-E-6-2-재활용`을 실제 문항과 맞춘다. 필수 문항이 없으면 실패해야 한다.
- 필수 사례/문항별 검사 목록을 선언하고 실행 결과를 대응시킨다. 필요한 검사가 0건 실행되거나 필수 자료·필수 범위가 없으면 성공 종료하지 않는다.
- 단순히 전체 문자열에 숫자나 `[1]`이 있다는 검사를 주요 근거로 삼지 않는다. **해당 문항의 값·단위·기간·범위·배지·검토 사유·출처**를 해당 행/영역에서 확인한다.
- 빈 `all(...)`로 범위 검사가 통과하지 않게 한다. 정상 합산 문항의 제한 범위와 근거 두 개, 실제 불일치 문항의 비교 사유, 범위 확인 문항의 체크리스트 행을 각각 요구한다.
- JSON은 재개봉 후 실제 저장 필드를 확인한다. Excel은 문항 ID로 행을 찾아 셀을 대조하고, PDF는 실제 문항과 값·사유가 연결된 영역을 확인한다.
- 검증기 자체의 음성 대조군도 둔다. 필수 문항 제거, 범위 삭제, 값 변경, 잘못된 페이지, 체크리스트 항목 누락을 각각 주면 해당 검사가 실패해야 한다.
- 실행되지 않은 검사는 ‘통과’가 아니라 누락/미실행으로 기록한다. 선택 검사의 skip과 필수 검사의 실패를 구분한다.

### 8-3. 실제 페이지와 렌더 확인

- 의사소통절차서는 실제 1쪽이다. PDF에서 얻은 0부터 세는 페이지 위치를 사용해 제출 표시가 p.1이 되게 한다. `page=1` 수동 입력을 반복하지 않는다.
- 여러 페이지 문서에서도 인용 문구의 실제 페이지를 확인한다. 위치가 불명확하면 임의의 페이지를 붙이지 않고 미확인 사유를 남긴다.
- 내부 node_id와 사용자 인용번호의 연결을 보존하고, 본문에서 실제 인용한 근거와 출처 목록을 맞춘다.
- 같은 ResponseSheet의 JSON·Excel·PDF를 다시 열어 대조한다. UI는 기존 AppTest 경로로 같은 값을 소비하는지 확인한다.
- PDF와 핵심 Excel 영역을 렌더링해 긴 검토 사유·헤더·근거·인용의 잘림과 겹침을 확인한다. Excel 렌더링을 하지 못하면 수행했다고 기록하지 않는다.
- PDF `vs` 등 읽을 수 있는 비교 표시와 폰트 회귀를 유지한다. 미지원 글자를 지우면서 수치·단위·비교 의미가 사라지지 않는지도 확인한다.

## 작업 10. 커밋·산출물·완료 보고

### 커밋 구성

같은 작업 브랜치에서 검토 가능한 단위로 새 커밋을 남긴다. 다음은 권장 구분이며 개수를 맞추려고 억지로 나누지 않는다.

1. 기간·행 문맥·합산 포함 관계와 실패 회귀.
2. 완결성·검증 자격·독립 문서 비교·상태 및 체크리스트 전달.
3. E-7/E-8 근거 적합성과 원문 충돌·문항 안내·호환성.
4. 검증 스크립트·실제 인용·3종 출력·검증기 음성 대조군.
5. 정정 산출물·결과 보고·출처 및 해시.

제품 동작 변경과 검증 변경이 추적되도록 각 커밋의 이유를 적는다. 기존 13개 커밋은 보존한다. main 병합은 하지 않는다.
